在教务系统中接入 Redis，是我第一次把一个看似简单的数据库查询变成“缓存优先、数据库回源、写入后失效”的完整访问流程。项目规模不大，也没有进行高并发压测，但它让我第一次认真思考：缓存到底应该存什么，数据变化之后要删除什么，缓存不可用时系统还能不能工作。

## 一、为什么要区分列表缓存和详情缓存

项目里有两类常见查询：一次读取全部学生，以及按 ID 读取单个学生。它们的访问语义不同，所以没有共用一个 Key，而是分别使用：

```text
students:all   -> 全部学生列表
student:{id}   -> 单个学生详情
```

列表缓存适合管理页面加载，详情缓存适合按编号查看。Key 结构直接表达了数据范围，也为后续失效操作提供了依据。如果所有查询都使用模糊或无规则的 Key，写操作发生时就很难判断哪些缓存已经过期。

## 二、采用 Cache Aside 的原因

当前实现采用常见的 Cache Aside 模式，应用层负责决定读取顺序和写入时机：

```text
读请求
  -> 先查 Redis
  -> 命中：直接返回
  -> 未命中：查询 MySQL
  -> 查询成功：写入 Redis
  -> 返回结果
```

它没有把 Redis 当成唯一数据源，MySQL 仍然保存学生数据。缓存丢失后，可以重新从 MySQL 构建；缓存只是为了减少重复的数据库读取。对当前学习项目来说，这种模式比把所有读写逻辑都放进缓存更容易理解，也更容易在故障时回退到数据库。

## 三、列表查询的实现路径

查询列表时，Service 先使用 `RedisTemplate<String, Object>` 读取 `students:all`。如果得到非空列表，就直接返回缓存结果；如果没有命中，则调用 `StudentMapper.findAll()`，通过 MyBatis XML 执行 `SELECT * FROM student`，然后将结果写入 Redis。

当前缓存 TTL 是 30 分钟：

```java
redisTemplate.opsForValue().set(
    ALL_STUDENTS_KEY,
    students,
    30,
    TimeUnit.MINUTES
);
```

设置过期时间可以避免缓存永久保留，但 TTL 本身不等于一致性保障。只要数据库在 TTL 到期前发生变化，缓存仍然可能暂时保存旧数据，所以写操作后的主动失效仍然是必须的。

## 四、详情查询与 Key 构造

按 ID 查询时，Service 会将 ID 拼接到 `student:` 前缀后面：

```text
student:1
student:2
student:100
```

命中时直接返回 Student；未命中时调用 Mapper 查询 MySQL，查询到对象后再写入缓存。详情 Key 和列表 Key 分开后，单个学生的修改可以精确清理详情缓存，同时清理列表缓存，避免详情和列表出现明显不一致。

从工程角度看，Key 构造不应该长期散落在业务方法里。当前项目用常量保存了 `student:` 和 `students:all` 前缀，已经比硬编码完整字符串更清楚；后续可以进一步抽出统一的 Key 工具、TTL 配置和缓存操作封装，避免不同 Service 重复实现一套不一致的规则。

## 五、写操作之后为什么必须失效

新增学生会改变列表，所以成功写入 MySQL 后删除 `students:all`。修改学生会同时影响列表和详情，因此需要删除 `students:all` 以及 `student:{id}`。删除学生也执行相同的两类失效：

```text
新增
  -> 写入 MySQL
  -> 删除 students:all

修改
  -> 更新 MySQL
  -> 删除 students:all
  -> 删除 student:{id}

删除
  -> 删除 MySQL 记录
  -> 删除 students:all
  -> 删除 student:{id}
```

项目使用的是“数据库写成功后删除缓存”，而不是先修改缓存对象。这样做的好处是逻辑简单：数据库是当前事实来源，下一次查询从数据库读取新值并重建缓存。它仍然存在短暂不一致窗口，也没有覆盖并发写入场景，但对于当前项目规模来说，边界清晰比过早引入复杂方案更重要。

## 六、空结果为什么也是一个问题

当前代码只有在查询结果非空时才写入列表缓存：

```java
if (students != null && !students.isEmpty()) {
    redisTemplate.opsForValue().set(...);
}
```

这意味着当数据库暂时没有学生数据时，每次请求都会再次访问 MySQL。它不一定立刻造成问题，但从缓存设计角度看，空结果也是一种可缓存的结果。后续可以使用短 TTL 缓存空列表，或者使用明确的空值标记，减少重复回源；同时要防止把“暂时没有数据”和“查询异常”混为一谈。

## 七、Redis 故障与当前未完成的降级策略

当前项目假设 Redis 可以正常连接，没有实现 Redis 不可用时自动降级到 MySQL 的逻辑，也没有针对 Redis 连接超时、序列化失败、缓存数据类型错误编写测试。

一个更完整的工程实现至少需要先明确策略：

- Redis 读取异常时，是否允许直接查询 MySQL。
- 回源成功后，是否还要尝试回填缓存。
- Redis 持续不可用时，是否需要限流、告警或熔断。
- 缓存中的旧数据结构无法反序列化时，是否删除坏 Key 后重新构建。

这些问题没有在当前项目中实现，因此本文只把它记录为工程边界，不把“配置了 Redis”写成“已经完成缓存高可用”。

## 八、如何验证这套缓存逻辑

当前测试主要验证 Spring Boot 上下文能够启动，还没有覆盖完整的缓存行为。后续可以为 Service 层补充至少这些场景：

1. 列表缓存命中时不调用 Mapper。
2. 列表缓存未命中时查询 MySQL 并写入 Redis。
3. 详情缓存命中时不访问数据库。
4. 新增成功后删除列表缓存。
5. 修改和删除成功后同时删除列表与详情缓存。
6. Mapper 返回空列表时验证空结果策略。
7. Redis 操作抛出异常时验证系统是否按约定降级。

测试的重点不是验证 RedisTemplate 的 API 能不能调用，而是验证缓存策略和业务写操作之间的关系。只有把这些场景写出来，缓存失效才不只是代码中的几行 `delete`。

## 九、这次工程实践留下的认识

Redis 缓存实践让我认识到，一个缓存方案至少要回答四个问题：数据源是什么，Key 如何组织，什么时候失效，故障时怎么办。教务系统目前完成了列表/详情缓存、30 分钟 TTL 和写操作后的基础失效，但没有完成空结果缓存、异常降级、命中率监控和真实并发验证。

这正是工程实践和技术名词堆叠的区别：不是项目里出现了 Redis，就可以宣称掌握了缓存，而是要能够解释它在当前业务中的作用、策略、边界和验证方式。后续在更复杂的项目中，我会继续把缓存和事务、并发、数据库事实源放在一起考虑，而不是把它当作一个孤立的加速开关。

这篇文章对应两个同类缺陷。工单 1008325 的表现是，党员发展模块中点击待办跳转后，用户没有进行任何处理，待办却变成了已办；工单 1008331 的表现是，活动管理移动端审批中点击查看详情，随后直接关闭页面，任务也被错误标记为已办。它们发生在不同模块和不同终端，但本质是同一个设计错误：查看待办和处理待办之间没有清晰的状态边界。

用户点击待办，只能证明他打开了任务，不能证明他已经完成审批、提交或确认。如果页面打开详情时就调用了“完成待办”接口，那么误触、返回、刷新和关闭页面都会造成业务事实被提前修改。本文从状态模型、接口职责、后端校验、事务一致性和多端回归几个方面，记录这类问题应该如何定位和修复。

## 一、先明确“已办”代表什么

待办状态不能只用一个布尔值，也不能把“看过”与“处理完”混为一谈。一个常见的状态模型是：

```text
TODO
  |
  v
PROCESSING
  |
  +----> DONE
  |
  +----> RETURNED

TODO ----> CANCELLED
```

`TODO` 表示任务已经生成，但当前用户还没有完成业务动作；`PROCESSING` 表示系统确实支持暂存或处理中状态；`DONE` 表示审批、提交或确认已经完成；`RETURNED` 表示任务被退回，等待再次处理；`CANCELLED` 表示业务流程取消，任务失效。

不同系统是否使用 `PROCESSING` 可以有所不同，但有一条原则不能改变：打开详情不等于 `DONE`。如果产品需要记录用户看过任务，可以单独增加 `viewed_at`、阅读状态或消息已读状态，但不能直接复用待办完成状态。一个用户看过任务后仍然可能没有填写意见、没有点击通过，也没有真正修改业务记录。

从业务事实看，“已办”至少应该对应一个明确动作：审批通过、审批驳回、提交确认、完成签收或其他被业务定义为完成的命令。状态名只是实现形式，真正要问的是：这个状态变化能不能被某个具体动作和操作记录证明。

## 二、错误实现为什么会触发问题

常见错误流程是：

```text
用户点击待办
   |
   v
前端跳转详情页
   |
   v
调用详情接口
   |
   v
详情接口内部顺便更新待办状态
   |
   v
TODO -> DONE
```

也可能写成前端的连续调用：

```ts
async function openTodo(todo) {
  await request.get(`/todo/${todo.id}`)
  await request.post(`/todo/${todo.id}/finish`)
  router.push(`/detail/${todo.businessId}`)
}
```

这段代码的问题不是请求顺序，而是第二个请求的触发条件错误。`openTodo` 表示“打开”，却调用了表示“完成”的命令。用户只要打开任务后按返回、关闭页面或刷新，就会把尚未处理的任务变成已办。

后端详情接口中顺便修改状态也同样危险。GET 请求在语义上应该负责读取资源，用户可能因为预加载、浏览器刷新、消息跳转或其他组件调用而触发 GET。如果 GET 具有副作用，调用方很难推断一次普通查询会修改哪些业务数据，也很难对它进行缓存和重试。

定位这类问题时，不能只看页面按钮。需要在浏览器开发者工具中记录点击前后的网络请求，确认是哪个请求修改了待办，再追到 Controller、Service 和 Mapper，检查详情查询是否调用了完成逻辑，或者移动端是否复制了一套与 PC 端不同的状态更新代码。数据库审计日志和服务日志也可以帮助确认状态变化发生的时间、操作者和请求入口。

## 三、把查询接口和处理接口分开

详情接口应该只读取：

```text
GET /todo/{id}
```

它可以返回待办基本信息、关联业务详情、当前状态和允许的操作，但不应该修改待办状态。真正的处理动作应该使用具有明确命令语义的接口：

```text
POST /todo/{id}/process
POST /todo/{id}/approve
POST /todo/{id}/reject
POST /todo/{id}/submit
```

例如审批任务只有在用户点击“通过”时，才调用：

```http
POST /todo/10001/approve
Content-Type: application/json

{
  "comment": "材料完整，审核通过"
}
```

前端逻辑应当把查看与处理拆成两个函数：

```ts
async function openTodo(todo) {
  const detail = await request.get(`/todo/${todo.id}`)
  detailData.value = detail.data.data
}

async function approveTodo() {
  await request.post(`/todo/${todoId}/approve`, {
    comment: form.comment,
  })
  await reloadTodoList()
}
```

打开详情只查询数据，点击处理按钮才发出改变状态的命令。这样用户即使打开后直接关闭，数据库中的待办仍然是 `TODO`。这也让接口语义更容易测试：调用 GET 前后状态应该不变，调用 approve 后才验证业务记录和待办状态一起变化。

## 四、后端要重新校验操作者和当前状态

接口职责分开之后，后端仍然不能依赖前端是否正确调用。任何处理命令都要重新确认待办存在、当前用户是被分配的处理人、任务状态允许处理，并且关联业务仍然处于可操作状态：

```java
@Transactional
public void approve(Long todoId,
                    Long operatorId,
                    String comment) {
    Todo todo = todoMapper.selectById(todoId);
    if (todo == null) {
        throw new BusinessException("待办不存在");
    }
    if (!todo.getAssigneeId().equals(operatorId)) {
        throw new BusinessException("当前用户不能处理该待办");
    }
    if (!"TODO".equals(todo.getStatus())) {
        throw new BusinessException("当前待办已经处理或已失效");
    }

    businessService.approve(todo.getBusinessId(), operatorId, comment);

    int updated = todoMapper.markDoneIfTodo(todoId, operatorId);
    if (updated != 1) {
        throw new BusinessException("待办状态已变化，请刷新后重试");
    }
}
```

数据库更新应把处理人和原状态都放进条件中：

```sql
UPDATE todo_task
SET status = 'DONE',
    process_time = NOW(),
    processor_id = #{operatorId}
WHERE id = #{todoId}
  AND assignee_id = #{operatorId}
  AND status = 'TODO';
```

影响行数为 1，说明这次请求成功取得处理权；影响行数为 0，说明任务已经被处理、取消、不属于当前用户或不存在。通过条件更新，可以防止用户处理别人的待办，也可以应对两个页面同时处理同一个任务。

业务记录本身也应该有状态条件或版本号。仅仅把待办更新为已办，并不能保证关联业务已经成功审批。推荐让业务状态、待办状态和操作日志位于同一事务中：业务审批成功，待办才标记完成，日志才记录成功；任一步失败，整体回滚。如果业务方法和待办方法分散在不同事务中，就可能出现页面显示已办但业务仍是待审核，或者业务已通过但待办仍留在列表中的不一致。

## 五、幂等不是只防止重复插入

待办处理接口必须考虑重复点击、网络重试和浏览器重复提交。理想行为是：第一次请求将 `TODO` 改成 `DONE` 并完成业务；第二次请求发现状态已经不是 `TODO`，直接返回“任务已处理”或让前端刷新，而不能再次执行业务核心逻辑和操作日志。

幂等可以依靠状态条件更新、业务版本号和操作唯一键共同完成：

```sql
UPDATE development_record
SET status = 'APPROVED',
    version = version + 1
WHERE id = #{businessId}
  AND status = 'PENDING'
  AND version = #{version};
```

如果接口需要支持客户端重试，也可以使用请求幂等键。服务端保存请求键与处理结果，重复请求返回同一结果，而不是重新执行一次审批。无论采用哪一种方案，目标都是让同一个业务动作最多产生一次有效状态转移。

还要注意前端按钮的防重复点击只能改善体验，不能作为唯一方案。用户可以打开多个标签页，移动端可以因为网络抖动重试，脚本也可以绕过按钮直接调用接口。真正的幂等边界必须落在服务端和数据库。

## 六、PC、移动端和消息入口共用规则

两个工单分别出现在党员发展模块和活动管理移动端，说明系统存在多个入口：PC 待办列表、移动端待办列表、消息通知跳转和业务详情页。如果每个入口自己实现一套“打开后怎么更新状态”的逻辑，迟早会出现一个入口正确、另一个入口错误的分叉。

更合理的结构是：不同终端只负责展示任务和调用统一的后端处理接口，状态转移规则集中在待办服务和具体业务服务中：

```text
PC 页面 ─┐
移动端 ──┼──> 统一待办查询和处理服务
消息跳转 ─┘              |
                         v
                 业务状态 + 待办状态 + 操作日志
```

如果移动端确实有特殊交互，例如需要暂存处理进度，也应该显式增加 `PROCESSING` 或草稿接口，而不是把“打开详情”当成完成。PC 和移动端的回归测试需要使用同一条测试数据，分别验证查看、返回、刷新、处理和重复处理后的最终状态。

## 七、测试设计和修复验证

这类 BUG 最关键的回归断言是：`GET` 详情接口前后，待办状态不能发生变化。具体场景至少包括：

- 打开待办但不处理，状态仍然是 `TODO`。
- 打开详情后直接关闭或返回，状态仍然是 `TODO`。
- 刷新详情页、重复进入详情页，不会改变待办状态。
- 点击通过、驳回或提交后，业务状态和待办状态按预期同时变化。
- 连续点击处理按钮或重复发送请求，不会重复执行业务。
- PC 端和移动端打开后关闭，都不会提前标记已办。
- PC 和移动端同时处理同一个任务时，只有一个请求成功。
- 无权限用户不能处理他人的待办，已完成或已取消任务不能再次处理。
- 业务保存失败时，待办不能被错误标记为完成。

除了接口测试，还要核对页面列表刷新和提示信息。处理成功后列表可以移除已办任务，处理失败时应保留待办并提示失败原因。不能只把页面上的卡片隐藏掉，因为数据库状态才是下一次查询的真实来源。

## 八、问题的工程价值

这次缺陷让我认识到，状态字段背后代表的是业务事实，而不是页面访问记录。“已办”应该意味着用户完成了某个明确业务动作，而不应该意味着用户打开过页面。类似错误还可能发生在消息通知被点击后错误标记为已读、审批页面打开后被错误标记为已审核、订单详情打开后被错误标记为已处理等场景。

修复这类问题的核心不是补一个判断，而是重新划清查询和命令的边界：查询接口保持无副作用，处理接口明确表达意图，后端统一做权限和状态校验，数据库条件更新保证并发下的单次转移，业务状态、待办状态和操作日志放在一致的事务里，最后用 PC、移动端和重复请求做完整回归。这样“看过”和“做完”才不会再被混成同一件事。

## 九、上线后的检查重点

这类修复上线后，不能只确认前端按钮已经移动到处理弹窗里。还应抽取一条待办，分别从 PC 端、移动端和消息入口打开，在每次查看之后直接查询数据库状态，确认仍然是 `TODO`；再执行一次明确处理，确认业务记录、待办和操作日志同时变化。对于已经存在的旧待办，要检查历史数据是否有被错误标记为 `DONE` 的情况，必要时通过可审计的脚本修正，而不是直接批量覆盖状态。

日志和监控也应关注状态转移异常，例如 GET 请求出现 UPDATE、待办完成数量明显高于实际审批数量、同一任务短时间内出现多次处理请求等。通过请求 ID 关联前端请求、后端服务日志和数据库操作，可以快速判断问题来自哪个入口。若多个模块都使用待办服务，还应把“查看不改变状态”作为公共契约写入接口测试，避免未来新增入口时再次复制错误逻辑。

在接口设计评审时，可以把所有方法按“查询”与“命令”分成两张清单。查询方法只允许读取，命令方法必须说明触发条件、状态前置条件、权限要求和幂等策略。代码评审时重点检查：GET 方法是否调用了更新 Mapper，详情组装是否隐藏了副作用，处理命令是否在数据库层再次校验状态，异常返回是否会让前端误以为处理成功。这样的检查比上线后依靠用户反馈更便宜，也更容易形成团队习惯。

对于已经被错误标记为已办的历史任务，修复程序也要谨慎。不能把所有 `DONE` 都无条件改回 `TODO`，因为其中可能确实已经完成。应根据操作日志、业务记录状态、处理时间和请求入口识别受影响范围，生成可审计的修复批次，并让管理员确认后执行。修复结果需要记录原状态、新状态、修复原因和执行人，避免为了修复当前问题又丢失历史事实。

从更长远的角度看，待办服务应该把状态转移封装成有限的命令集合，而不是允许各模块直接更新状态字段。模块只提交“审批通过”或“审批驳回”这样的业务意图，统一服务负责校验和落库。这样新增入口时复用的是同一套规则，状态字段不会因为页面开发方便而被任意修改。

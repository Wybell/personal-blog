2026 年 5 月到 8 月，我在广州平云信息技术有限公司进行 Java 全栈开发实习，参与企业级组织管理平台的开发与维护。这段经历对我来说，不只是第一次进入真实团队写代码，更重要的是让我第一次完整经历了从需求理解、代码实现、前后端联调、测试验证到上线交付的工作流程。

在实习期间，我累计完成了 73 个经过测试并上线的工单，其中包括 41 个需求和 32 个缺陷。工单数量本身并不能完全代表工作质量，但它让我接触到了很多真实业务场景，也让我逐渐理解：企业开发并不是把某个接口写出来就结束，而是要让功能能够被正确使用、通过测试、顺利上线，并且在出现问题时能够快速定位和修复。

## 一、从学校项目到真实业务

在进入实习之前，我主要通过个人项目学习 Java、Spring Boot、MySQL、Redis 和前端技术。学校项目和个人项目通常由自己决定需求，遇到问题时也可以直接调整设计。但企业项目不同，很多功能已经存在于一个比较复杂的业务系统中，开发者不能只关注眼前的页面和接口，还要理解原有数据结构、用户角色、权限边界以及其他模块对当前功能的影响。

刚开始接触工单时，我需要先判断这个问题属于需求变更、功能缺陷、数据问题，还是前后端联调问题。一个看起来很小的页面问题，背后可能涉及接口返回字段、权限判断、数据库查询条件和前端展示逻辑。只有先把问题所在的链路梳理清楚，后面的修改才不会变成反复试错。

因此，我逐渐形成了一个基本流程：先阅读工单和需求描述，再复现问题，确认实际表现和预期表现之间的差异，然后查看相关页面、接口、业务代码和数据，最后确定修改范围。对于比较复杂的问题，我会先把问题拆分成几个小部分，分别确认是前端、后端、数据库还是权限逻辑导致的。

## 二、我实际参与的工作内容

实习期间接触到的业务范围比较广，主要包括审批、待办、组织权限、费用导入、文件下载、分页、批量导入校验、JSON 解析、数据权限和前后端联调等内容。

审批和待办类功能让我开始理解状态流转的重要性。一个审批对象通常不是简单地从“未处理”变成“已处理”，而是会经历创建、提交、审批、驳回、撤回或结束等多个阶段。不同状态下能够执行的操作不同，页面按钮的显示也不同。如果只修改了某个按钮，却没有同步修改后端状态校验，就可能出现页面看起来不能操作，但接口仍然可以被直接调用的问题。

因此，在处理这类问题时，我会关注两个方面：第一，前端展示是否和当前状态匹配；第二，后端是否真正对状态和用户权限进行了校验。前端按钮隐藏只能改善使用体验，不能作为真正的安全边界。真正的权限判断必须在后端完成。

组织权限和数据权限让我进一步认识到，登录认证和业务权限并不是一回事。用户能够登录系统，只能说明用户身份被确认，并不代表他可以查看或修改所有数据。某些数据可能只允许本人查看，某些数据只能由部门负责人处理，还有一些操作只有特定角色才能执行。

在排查权限问题时，我需要同时关注当前用户身份、角色信息、组织关系、数据所属范围以及接口中的查询条件。如果只在前端限制页面入口，而后端没有加入对应的数据过滤，就可能出现用户通过直接调用接口查看不属于自己的数据。因此，权限问题往往不能只修改一处代码，而需要确认前端、接口和数据查询是否保持一致。

## 三、批量导入和数据校验

批量导入是我参与比较多的一类功能。批量导入通常涉及文件读取、字段解析、数据类型转换、必填字段校验、重复数据判断和错误信息返回。它和普通表单提交不同，一次请求里可能包含很多条数据，只要其中一部分处理不当，就可能导致导入结果不符合预期。

处理批量导入问题时，我会重点关注几个方面：文件是否为空，表头是否符合要求，字段类型是否正确，必填字段是否缺失，数据格式是否符合业务规则，以及异常数据是否能够被准确提示。

JSON 解析也是实习中接触到的一类问题。后端接收到的 JSON 数据不一定总是严格符合预期格式，字段可能缺失、类型可能不一致，甚至可能出现空字符串、空数组或嵌套结构异常。如果代码只按照理想数据编写，就容易在真实请求中出现解析异常。

这类问题让我意识到，参数校验不能只依赖前端。前端校验主要是为了提升用户体验，后端校验才是保证系统数据正确的最后一道防线。对于错误数据，系统应该尽量返回明确的错误位置和原因，而不是只抛出一个用户无法理解的异常信息。

## 四、分页、文件下载和前后端联调

分页问题看起来比较基础，但实际处理时需要同时确认前端页码、每页数量、后端分页参数、数据库查询结果和总数量统计是否一致。如果前端从第 1 页开始，而后端从第 0 页开始，就可能出现数据错位；如果查询列表和查询总数使用了不同的筛选条件，页面显示的总页数也会不准确。

文件下载功能则让我接触到了接口响应类型、文件流、文件名处理和权限校验等问题。文件下载不能只判断按钮是否显示，还要确认后端是否检查当前用户是否有权访问目标文件。对于文件名、路径和返回内容，也需要避免因为参数处理不当造成安全问题。

前后端联调是实习中非常常见的工作。很多问题并不是单纯的前端错误或后端错误，而是双方对接口约定理解不一致。例如后端返回字段名称发生变化，前端仍然读取旧字段；后端返回的数据结构增加了一层，前端却按照原来的结构解析；前端传递的参数名称和后端接收的参数名称不一致；接口返回成功，但页面没有按照新的状态刷新。

遇到这类问题时，我会先使用浏览器开发者工具查看实际请求和响应，再对照后端接口定义和前端调用代码，确认问题发生在请求参数、响应结构还是页面状态更新。相比直接猜测代码哪里有问题，先观察真实网络请求通常能够更快缩小范围。

## 五、我处理缺陷时形成的方法

处理缺陷时，我逐渐形成了“复现、定位、修改、回归、验证”的流程。

第一步是复现问题。只有能够稳定复现，才知道修改是否真正有效。如果问题无法复现，就需要记录出现条件，例如用户角色、数据状态、操作顺序、浏览器行为或具体请求参数。

第二步是定位原因。我会根据问题表现判断排查方向：页面显示错误，优先查看接口响应和前端渲染；接口返回错误，继续查看 Controller、Service 和异常日志；数据结果不正确，则进一步检查 SQL、查询条件和数据库数据；权限异常，则需要对照用户角色、资源归属和数据范围。

第三步是修改代码。修改时尽量控制范围，不随意改变与当前问题无关的逻辑。对于缺陷修复，最重要的不只是让当前案例通过，还要考虑相同逻辑的其他入口是否也会受到影响。

第四步是回归测试。一个问题修复后，需要重新验证原来的错误场景，也要检查正常场景、边界场景和相关功能，避免修复一个问题后引入新的问题。

第五步是上线验证。测试环境通过并不代表线上一定没有问题。上线后还要确认页面、接口和关键数据是否正常，必要时查看日志和实际请求结果。测试人员验证没有问题后，工单会按照团队流程关闭。

实习期间，苏辰负责测试相关工作，通常由测试验证通过后关闭工单。这个流程让我认识到，开发人员的“代码修改完成”和工单的“流程关闭”并不是同一个概念。前者代表实现工作完成，后者还需要经过测试验证和流程确认。离职前最后几项工作我已经完成并通过了相应验证，只是因为离职交接，工单系统中没有来得及完成关闭。这也让我认识到，项目交接和状态记录同样属于工程工作的一部分。

## 六、这段经历带给我的变化

实习前，我更容易把一个功能理解成“页面、接口和数据库”。实习之后，我开始从完整业务流程理解功能：谁可以操作，什么时候可以操作，操作之后状态如何变化，数据是否会被重复处理，异常情况下是否会留下脏数据，测试之后如何确认上线结果。

我也逐渐意识到，代码质量不仅体现在能不能运行，还体现在几个方面：

- 需求是否真正理解；
- 修改范围是否合理；
- 权限和数据范围是否正确；
- 异常输入是否能够处理；
- 前后端约定是否一致；
- 测试是否覆盖了主要场景；
- 上线后是否能够验证结果；
- 离职或交接时是否留下清晰记录。

这段实习让我接触了很多不同类型的问题，也让我发现自己在项目经验、代码理解和工程实践方面仍然有很多需要提升的地方。企业项目中的代码量和业务复杂度，确实比个人项目更高，但更重要的是，它让我学会了如何在已有系统中工作，而不是只从零开始搭建自己的代码。

## 七、总结

这段实习对我最大的意义，是让我从“完成一个功能”逐渐走向“完成一个闭环”。

我累计完成了 73 个经过测试并上线的工单，其中包括 41 个需求和 32 个缺陷。通过这些工作，我参与了需求理解、业务开发、前后端联调、问题定位、测试验证和上线跟踪，也接触到了审批、组织权限、批量导入、数据权限、文件处理和分页等真实业务场景。

我目前仍然把自己定位为正在成长中的 Java 后端开发者，而不是已经完全成熟的工程师。实习让我积累了真实的业务开发和交付经验，AI 面试助手和 EventFlow 则让我继续练习产品闭环、事务、权限、数据一致性和部署。接下来，我会继续补充 Java 后端基础、算法和面试知识，同时把实习和项目中的实际问题整理清楚，让自己不仅能够完成代码，也能够解释代码为什么这样设计、问题是如何定位的，以及一个功能怎样才能真正走到上线。

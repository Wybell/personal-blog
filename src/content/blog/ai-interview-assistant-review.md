## 写在前面

AI 面试助手是我做的第二个相对完整的项目。最开始它的需求非常简单：输入一个知识点，让 AI 生成一道面试题，再提交答案获得评分。但真正开始开发之后，我发现“调用一次模型”距离“做出一个可以持续使用的产品”还有很长的距离。

用户不会只想要一道孤立的问题。他可能想根据自己的简历练习，想限定某一个专题，想选择 Java 或 TypeScript，想模拟初轮技术面，也可能在进行到一半时关闭页面，第二天回来继续，最后再查看一份完整复盘。只要这些需求同时出现，系统就必须处理用户、简历、面试会话、题目、回答、评分、模型偏好和历史记录之间的关系。

因此，这个项目的核心并不是“接入了 AI”，而是围绕 AI 输出的不确定性，建立了一套相对稳定的业务流程。本文记录这个项目的真实实现、设计取舍、遇到的问题和没有继续过度扩张的边界。

## 一、项目目标和整体架构

项目面向正在准备实习、校招或社招技术面试的求职者，主要流程是：

```text
注册/登录
   -> 上传并预览简历
   -> 选择训练方向、语言和出题来源
   -> 生成单题并提交回答
   -> 获取评分、参考答案和改进建议
   -> 创建模拟面试
   -> 完成主问题与追问
   -> 生成结构化复盘
```

技术栈如下：

- 后端：Java 17、Spring Boot 2.7.18、Spring Security、MyBatis-Plus
- 前端：Vue 3、TypeScript、Pinia、Element Plus
- 数据：MySQL 8、Redis 7
- AI：统一客户端抽象，支持 DeepSeek 和可选的中转模型
- 流式交互：SSE，用于评分过程的增量反馈
- 文件处理：PDF、DOCX、TXT 简历文本提取
- 工程交付：Maven、Vitest、Docker Compose、Nginx、GitHub Actions
- 云端：腾讯云单机 Docker 部署，宿主机 Nginx 负责 HTTPS 和反向代理

虽然项目采用单体架构，但代码边界按照业务职责拆分，而不是把所有逻辑写在 Controller 中：

```text
Controller
  -> Service
      -> Mapper / Redis / AI Client
          -> MySQL / 外部模型服务
```

Controller 只接收 HTTP 参数、校验请求并返回 DTO；Service 负责业务规则；Mapper 负责数据库访问；AI Client 负责请求构造、认证、响应解析和错误处理。这样做的直接收益是，替换模型供应商时不需要改动模拟面试和评分业务。

## 二、先建模，再接入 AI

这类项目最容易走入的误区是先写一个“调用 AI 的方法”，然后把所有输入拼成字符串传给模型。这样很快能跑通 Demo，但后续会遇到几个问题：历史记录无法关联、同一个用户可能读取到别人的内容、模型更换后业务代码大量修改、一个请求失败时无法判断应该重试还是结束流程。

我先把领域拆成几组相对独立的数据：

- `user`：账号、密码哈希和用户身份。
- `resume_document`：简历文件元数据、私有存储路径和提取后的文本。
- `knowledge_topic`：按方向和语言组织的专题内容。
- `ai_model`、`ai_model_policy`、`user_ai_preference`：模型目录、默认策略和用户模型偏好。
- `answer_record`：普通练习中的问题、回答、评分和实际使用的模型。
- `mock_interview_session`：一轮模拟面试的岗位、公司、轮次、状态和问题上限。
- `mock_interview_turn`：主问题、追问、回答和逐题评分。
- `mock_interview_review`：一轮面试最终的统计结果和结构化复盘。

这里有两个重要的设计决定。

第一，用户偏好的模型不是直接存 provider 字符串，而是关联 `ai_model` 的 ID。前端只能提交允许列表中的 `modelId`，不能提交任意接口地址、模型名或 API Key。这样可以避免把外部配置暴露给前端，也能在后台禁用某个模型，而不需要修改前端代码。

第二，模拟面试的回答记录不能只保存成一段最终文本。主问题和追问需要通过 `turn_type`、`parent_turn_id`、`follow_up_no` 和 `sequence_no` 表达关系，否则复盘时无法判断某个回答是对主问题还是对追问作出的。数据库中的约束还限制了追问次数为 1 到 2，避免只依赖前端按钮状态。

## 三、三种出题来源和轻量知识库

普通练习目前有三种互斥模式：知识库专题、自定义知识点和技术知识点。

### 1. 知识库专题

用户选择一个已经发布的专题文档，系统根据专题内容出题。后端不会只根据专题 ID 查询内容，还会同时校验当前方向和语言，并且只允许读取已发布且有可用正文的专题。

专题上下文有长度上限，当前会截断到 8,000 个字符。这个限制解决了两个问题：一是避免把过大的文档直接塞进模型上下文，二是让单次请求成本和延迟保持在可控范围内。这个功能是专题级检索和上下文拼装，不是向量数据库，也没有把它包装成复杂的 RAG 系统。

为了减少重复题目，Redis 保存用户在某个方向、语言和专题下的历史问题。历史记录最多保留 50 条，过期时间为 30 天。生成新题时，后端把历史问题交给 AI 作为排除条件；返回后还会在服务端做一次规范化比较，最多重试两次。如果模型仍然返回重复问题，系统会返回最后一次结果，而不是无限调用外部服务。

相关缓存键包含用户、模型、出题模式、方向、语言和专题 ID，类似：

```text
question:{userId}:model:{modelId}:{mode}:{direction}:{language}:topic:{topicId}
```

模型 ID 必须进入缓存键，否则用户切换模型后可能读到另一个模型生成的旧题目，这是一个很隐蔽但实际存在的数据隔离问题。

### 2. 自定义知识点

用户可以直接输入想练习的内容，例如“Java 并发包”“Redis 缓存一致性”或“Vue 响应式原理”。这种模式不依赖知识库，后端只校验输入非空且不超过长度限制，再把它作为模型上下文的一部分。

### 3. 技术知识点

用户先选择前端或后端方向以及语言，再从服务端维护的技术主题目录中选择知识点。后端会再次验证方向、语言和知识点的组合是否合法，不能只相信前端下拉框传来的值。

这三种模式在接口层使用枚举表达，而不是让前端传一段自由文本。这样能把“题目来源”变成明确的业务状态，也能避免知识库专题和自定义知识点同时生效。

## 四、AI 客户端抽象和运行时模型选择

项目经历过一次从“启动时选择供应商”到“用户运行时选择模型”的改造。最初通过环境变量决定使用哪个 AI Provider，这种方式适合单一部署，但用户每次切换模型都需要重启后端，无法满足前端的模型选择需求。

现在的设计是所有客户端同时由 Spring 管理，`AiClientRegistry` 根据数据库解析出的有效模型进行路由：

```text
用户选择 modelId
   -> UserAiPreferenceService 校验并保存偏好
   -> 解析有效模型和 provider
   -> AiClientRegistry 路由
   -> DeepSeekAiClient / CustomResponsesAiClient
```

`AiClient` 抽象至少覆盖普通文本生成、评分和流式文本生成。DeepSeek 客户端按 Chat Completions 结构组装 `messages`，中转客户端按 Responses 结构组装 `instructions`、`input`、`reasoning.effort` 和 `store` 等字段。它们对上层业务隐藏了协议差异。

模型配置放在外部配置文件和环境变量中，数据库只保存非敏感的 provider、模型编码和显示名称。缺少 API Key 或 endpoint 时，后端抛出非敏感的“AI 服务配置不完整”错误，日志也只记录异常类型，不打印密钥和完整请求体。

### 模型返回不稳定是一个业务问题

接入 AI 后最早遇到的一个问题是：有些模型一次返回多道题，有些模型返回英文，有些模型响应慢到前端以为请求失败。只在提示词里写“只输出一道中文题”并不能完全解决，因为外部模型的输出不是强类型接口。

因此我做了三层处理：

1. 提示词明确角色、语言、输出格式和题目数量。
2. 后端对响应文本做清洗和结果校验，业务层只接收可展示的题目文本。
3. 前端只展示当前题目，下一题由用户明确触发，避免把模型的一次长响应渲染成整页问题。

这并不能保证模型永远正确，但它把“模型偶尔不听话”从页面崩溃，降级成一次可控的业务失败。

## 五、模拟面试是一个状态机

模拟面试不是普通的“连续调用生成接口”，而是一个有状态的流程。会话状态包括：

- `ACTIVE`：可以回答当前问题、生成下一道题或追问。
- `COMPLETED`：完成本轮全部主问题并生成总结。
- `ENDED_EARLY`：用户中途主动结束，保留已完成记录但不可继续答题。

当前四种轮次的默认主问题数量是：初轮技术面 8 道、深入技术面 12 道、综合终面 10 道、HR 面 4 道。这个上限写入会话的 `question_limit`，而不是每次动态从前端读取。这样即使后续调整默认配置，已经开始的面试也不会中途改变目标数量。

回答主问题时，服务端会检查：

- 会话是否属于当前 JWT 用户。
- 会话是否仍为 `ACTIVE`。
- 提交的 turn 是否属于当前会话。
- 提交的是否是最新未回答问题，不能跳过前面的题。
- 当前题目是否已经回答过。

生成下一题前，服务端要求当前问题已经回答，并且主问题数量没有达到上限。生成追问时，服务端要求目标是主问题、当前问题已回答，并统计该主问题已有的追问数量，超过两次直接返回 409。前端按钮只是交互入口，真正的规则在后端执行。

## 六、简历文件和历史数据为什么要分开

简历属于用户的私有文件，当前支持 PDF、DOCX 和 TXT，单文件最大 10 MB。上传过程大致是：

```text
校验登录用户
   -> 校验文件大小和扩展名
   -> 提取文本
   -> 拒绝空内容
   -> 生成私有存储路径
   -> 保存文件和数据库元数据
```

上传成功后，数据库保存原始文件名、内容类型、存储路径和提取文本。预览接口只返回当前用户拥有的记录，不能根据一个任意 resumeId 直接读取文件。

简历删除是后续改动中最容易出问题的地方。最初如果直接删除简历记录，外键可能阻止删除；如果级联删除，又会把已经完成的面试历史一起删掉，这显然不符合用户预期。

最后采用了“文件生命周期”和“面试历史生命周期”分离的方案：

- 仍有 `ACTIVE` 会话使用简历时，不允许删除。
- 会话完成或提前结束后，允许删除简历文件和简历记录。
- 面试会话将原始文件名保存为快照。
- 历史题目、回答、评分和复盘独立保留。
- `mock_interview_session.resume_id` 对已结束历史允许为空，并使用 `ON DELETE SET NULL`。

这个取舍比简单地把所有相关记录级联删除更符合业务，也让我意识到文件表不应该成为历史业务数据的唯一锚点。

## 七、复盘生成和失败隔离

复盘服务单独拆成 `MockInterviewReviewService`，负责会话归属校验、结束状态校验、客观统计、转录组装、AI JSON 解析和复盘持久化。

复盘数据包含：已回答数量、主问题数量、追问数量、平均分、整体反馈、优势、优先改进项和训练建议。平均分由后端基于已保存的评分计算，不让 AI 自己随意编一个数字；文字反馈才交给 AI 生成。

正常完成面试后，系统会自动尝试生成复盘。如果 AI 调用超时或返回格式错误，面试状态仍保持 `COMPLETED`，用户可以从复盘页面手动重试。提前结束的会话不自动消耗一次复盘调用，而是在用户主动请求时生成。这种设计把核心业务状态和非核心的 AI 总结状态分离，避免 AI 服务短暂异常导致用户已经完成的面试被回滚。

## 八、SSE 流式评分的实现和坑

评分接口既需要调用外部模型，又希望用户看到处理过程，所以采用 SSE。后端把 SSE 连接、异步线程和业务评分拆开：

- `InterviewService` 负责解析当前用户、选择模型、调用评分业务并保存 `answer_record`。
- `InterviewScoreSseAdapter` 负责创建 `SseEmitter`、调度异步任务、发送事件和结束连接。
- `SseExecutorConfig` 提供 Spring 管理的线程池，避免每个请求临时创建线程池。
- AI Client 负责读取外部流式响应，并通过 delta consumer 把增量文本传给适配器。

流式响应的难点不在于“把字符串写到连接上”，而在于连接断开、外部请求失败、客户端取消和最终结果落库的顺序。如果只在 Controller 中拼接这些逻辑，异常分支很快会和业务代码混在一起。当前的原则是：SSE 断开只影响传输层；评分是否成功、是否保存回答记录由业务层决定；敏感信息不进入事件内容。

项目还保留了旧静态页面的 SSE URL Token 兼容逻辑，但它被限制在旧评分接口，不向其他接口扩散。正式的 Vue 前端接口使用 Bearer Token，后续如果继续演进，会优先统一流式请求的认证方式。

## 九、安全设计不是只加一个 JWT

项目使用无状态 JWT，密码使用 BCrypt。安全链由 `JwtAuthenticationFilter` 将 Bearer Token 转换成 `JwtUserPrincipal`，并放入 Spring Security 的 `SecurityContext`。业务代码通过 `UserContext` 获取用户，而不是接受前端传来的 userId。

接口权限分为两类：登录注册、静态资源和必要的文档入口放行；简历、题目、面试、复盘、错题本和模型偏好等业务接口统一要求认证。缺失、非法或过期 Token 返回统一格式的 401，认证成功但没有权限返回 403。

此外还要防止“有 Token 但访问了别人的数据”。例如简历预览、简历删除、面试会话查询、回答提交和复盘查询，都在 Service 层通过 `userId + resourceId` 查询归属。这个校验不能只放在前端隐藏按钮，也不能只依赖 URL 中的 ID。

AI 场景还存在提示词注入问题。用户的简历内容、专题内容和回答都属于不可信输入，不能让它们覆盖系统规则。因此提示词把系统指令和用户内容分开，模型输出进入后端校验，不把用户输入拼成新的系统指令。当前这是一套基础防护，不声称可以防住所有模型攻击，但至少明确了信任边界。

## 十、Redis 和 MySQL 的职责边界

项目中的核心事实都落在 MySQL：用户、简历元数据、面试会话、题目、回答、评分和复盘。Redis 只存可重建或有过期时间的数据，主要包括题目缓存和专题练习历史。

题目缓存设置过期时间，缓存键包含用户和模型，避免跨用户、跨模型复用。专题历史设置 30 天过期并限制最大长度，避免用户练习时间很长后 Redis 列表无限增长。

这里的一个实际教训是：缓存不是“加上就更快”。如果缓存键没有覆盖业务维度，缓存会产生错误结果；如果核心记录只写 Redis，服务重启后历史就会消失。缓存失效或 Redis 暂时不可用时，业务应该尽量回退到数据库或重新生成，而不是把 Redis 当成唯一数据源。

## 十一、Flyway 迁移和数据库兼容

数据库结构全部通过版本化 SQL 管理，当前迁移从 V1 逐步演进到 V13，覆盖模型选择、知识库、简历、模拟面试、公司信息、会话状态和复盘表。

已经执行过的迁移不能直接修改。比如最初的模拟面试表只支持三轮、问题上限固定为 8；后续新增 HR 面、12 道题和追问能力时，我新增 V10 修改约束和字段，而不是回头改 V1。简历历史保留和提前结束状态也分别通过 V11、V12 演进，复盘通过 V13 新增。

这种方式会让 SQL 文件数量增加，但能保证本地、CI 和服务器按相同顺序得到相同结构。生产发布时，后端代码和对应 Flyway 迁移必须作为同一个发布单元，并在迁移前保留数据库备份和恢复方案。

## 十二、Docker 和腾讯云部署中的实际问题

本地 Docker 构建曾经遇到过几个很具体的问题。

第一个问题是 Windows Maven Wrapper 和 Linux 容器环境不完全一致。最初让 Docker 直接依赖本机 `target/*.jar`，换机器或没有先打包时就会失败。后来改成 Maven 多阶段构建，由镜像内的 Maven 完成源码编译，并通过 `.dockerignore` 排除本地构建产物和环境文件。

第二个问题是容器内访问 Maven Central 时默认解析到了不可用的 IPv6 地址，构建表现为依赖下载超时或 TLS 失败。构建阶段强制 JVM 优先使用 IPv4，并增加公共 Maven 镜像配置，才让构建链路稳定下来。这个问题与 Java 代码无关，却会直接影响能不能发布，说明部署环境本身也是项目的一部分。

第三个问题是本机端口和服务器端口不能想当然地复用。服务器上已经运行着另一个项目，80、443、8082、8083 等端口各有用途。AI 面试助手的前端容器只绑定 `127.0.0.1:8085`，后端绑定 `127.0.0.1:8082`，外部访问交给宿主机 Nginx。这样可以避免把前端、后端和数据库端口直接暴露到公网，也避免与另一个项目抢占入口端口。

生产 Compose 中，MySQL 数据卷和 Redis 数据卷独立持久化；简历文件挂载到服务器外部目录，后端配置文件以只读方式挂载到容器。真实密码、JWT Secret 和 AI Key 不在仓库中，发布时由服务器外部配置提供。

## 十三、CI 和手动 CD

GitHub Actions 的 CI 分为后端和前端两条任务：

后端 Runner 启动隔离的 MySQL 8 和 Redis 服务，注入只用于 CI 的占位配置，开启 Flyway 后执行 Maven 全量测试。这样 CI 不依赖我本机是否安装了数据库，也不会连接生产库。

前端执行依赖安装、ESLint、Vitest 和生产构建。当前已经通过了后端 118 个测试以及前端 lint、12 个 Vitest 测试和生产构建验证。

CD 没有设置成每次代码推送都自动上线，而是由我在 GitHub Actions 中手动触发。发布流程会固定检出 `main` 的最新提交，经过 SSH 连接服务器，执行部署脚本，构建并启动容器，等待 MySQL、Redis 健康检查，执行 Flyway 迁移，最后检查前端回环地址返回 200、后端受保护接口返回 401。

选择“自动 CI + 手动 CD”是因为个人项目线上只有一台服务器，线上数据库和用户数据比自动化速度更重要。CI 负责证明代码可以测试和构建，CD 负责把已经确认的版本发布出去。未来如果多人协作，可以再增加 `main` 分支保护、环境审批和自动回滚。

## 十四、踩过的坑和最后留下的经验

### 模型选择不能直接等于环境变量

环境变量适合放密钥和 endpoint，不适合承载每个用户的运行时选择。把 `AI_PROVIDER` 作为全局开关时，切换模型必须重启后端；改成模型目录加用户偏好后，选择行为成为普通业务数据，客户端路由也更容易测试。

### 提示词不能代替业务校验

提示词可以约束模型，但不能替数据库约束、服务端校验和输出解析。题目只能展示一题、追问只能两次、专题不能越权读取、面试完成后才能复盘，这些规则都必须在后端执行。

### 删除文件不等于删除业务历史

简历文件是当前用户的资料，面试记录是训练历史，两者需要不同的生命周期。直接级联删除看起来简单，却会让用户删除旧简历后丢失复盘数据。

### 外部服务失败不能拖垮核心状态

复盘 AI 调用失败时，不能把已经完成的面试改回进行中；流式连接断开时，也不能重复保存评分；模型配置不完整时，错误信息不能泄露配置细节。失败隔离比“所有请求必须成功”更现实。

### 线上问题经常不在业务代码里

Docker 引擎没有启动、服务器端口被占用、Nginx 仍然指向旧前端、容器内 DNS 优先走 IPv6、生产配置没有挂载成功，这些都可能表现成“页面打不开”或“AI 请求一直转圈”。因此发布检查必须覆盖容器状态、端口监听、Nginx 配置、日志、数据库迁移和接口健康检查。

## 十五、项目边界和下一步

这个项目目前是单机 Docker Compose 部署的个人项目，数据库和 Redis 都在同一台腾讯云服务器上；知识库是轻量专题检索，不是向量数据库；模型调用依赖外部服务，也没有宣称自研大模型、海量题库或高并发压测结果。

如果继续演进，比较有价值的方向是：增加更完整的调用日志和成本统计，引入限流与重试策略，补充异步任务和失败补偿，完善监控告警，进一步统一 SSE 的请求头认证，并在知识库内容规模真正增长后再评估向量检索。它们都应该由真实问题驱动，而不是为了堆技术名词。

对我来说，这个项目的含金量不只在于页面上出现了 AI。更重要的是，我完整经历了需求调整、数据建模、外部服务适配、权限校验、异常处理、测试、数据库迁移、容器化、服务器排障和持续交付。它让我开始把“能在本地运行”与“能够被用户稳定使用”区分开来。

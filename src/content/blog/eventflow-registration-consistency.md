在 EventFlow 的活动报名中，最容易被低估的问题不是“点击报名后插入一条记录”，而是名额有限时，多个请求同时到达会不会把剩余名额扣成负数，或者出现名额已经减少但报名记录没有保存的情况。

## 先把业务规则说清楚

一个报名请求至少要满足这些条件：活动存在并且已经发布，场次属于当前活动，场次处于可报名状态，当前时间位于报名窗口内，用户没有报名过同一活动，并且场次仍有剩余名额。前端可以根据这些条件决定按钮是否展示，但最终判断必须在后端完成，因为请求可以绕过页面直接发送到接口。

这些检查解决的是业务边界和权限问题，但它们还不能单独解决并发问题。假设场次只剩一个名额，两个请求先后执行查询，都可能读到“剩余一个”，然后各自通过 Java 代码里的判断。此时如果再分别执行扣减，就可能发生超卖。

## 把读取和扣减合成一个数据库动作

EventFlow 使用 MySQL 条件更新，把“还有名额”和“扣减名额”放进同一条 SQL：

```sql
UPDATE ef_activity_session
SET available_quota = available_quota - 1,
    confirmed_quota = confirmed_quota + 1
WHERE id = ?
  AND activity_id = ?
  AND status = 'ACTIVE'
  AND available_quota > 0;
```

服务层根据这条 SQL 的影响行数判断结果。影响行数为 1，说明数据库执行更新时满足了场次归属、状态和剩余名额条件，当前请求成功拿到一个名额；影响行数为 0，说明名额已用尽，或者场次状态已经发生变化，接口返回冲突结果。

这里的关键不是在 Java 中提前查一次库存，而是让数据库在执行更新的瞬间完成最终判断。即使多个请求同时到达，也只有满足 `available_quota > 0` 的更新能够成功，应用层不会把一个已经失效的查询结果当成最终事实。

## 用唯一约束防止重复报名

报名表 `ef_registration` 上有活动和用户的联合唯一约束：

```sql
UNIQUE KEY uk_ef_registration_activity_user (activity_id, user_id)
```

它表达的是明确的业务规则：同一用户对同一活动只能保留一条报名事实。这个约束没有把 `session_id` 放进去，因为用户不能通过更换场次绕过同一活动只能报名一次的限制。

服务层会先查询已有报名，用于给用户更清楚的提示；但这个查询不是并发安全的最终保障。真正的底线仍然是数据库唯一索引。对于已经取消过报名的用户，系统可以在满足条件时重新激活原记录，而不是让数据库里出现多条同一活动的报名记录。

## 用事务保证两件事不能只成功一半

名额扣减和报名记录写入属于同一个业务动作。报名服务放在 `@Transactional` 方法中：先校验活动、场次和用户状态，再执行条件扣减，最后新增或更新报名记录。如果后续写入失败，事务会回滚已经完成的名额变化，避免数据库出现“名额少了，但报名记录不存在”的半成功状态。

取消报名时则执行相反方向的流程：确认当前用户确实有一条已确认报名，条件更新释放一个名额，再把报名状态改为 `CANCELLED`。释放名额和更新报名状态也必须在同一个事务里完成。

## 这次实践留下的判断

这个功能最终依靠的是多层保护，而不是某一个技术名词：服务层负责活动状态、时间窗口和资源权限，数据库条件更新负责有限名额的原子扣减，唯一约束负责重复报名，事务负责多个写操作的一致性。

当前项目已经完成这些业务实现并完成部署验证，但还没有专门的数据库并发压测，也没有完整的浏览器端 E2E 测试。因此我会把“设计上考虑了并发”和“已经用压测证明了并发能力”区分开。Redis 和 RabbitMQ 虽然已经作为基础设施接入项目配置，但当前报名主链路没有依赖它们完成名额扣减，后续是否使用要由实际的缓存、通知或异步任务需求决定。

对我来说，EventFlow 的价值不只是实现了一个报名按钮，而是让我开始把功能完成、数据正确和工程验证分别看待：页面能操作只是起点，真正重要的是异常和并发情况下，系统仍然能守住业务规则。

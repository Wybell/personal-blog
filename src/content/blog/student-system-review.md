教务系统是我真正开始理解后端项目结构的第一个项目。它的功能并不复杂，核心是学生信息的增删改查和用户登录，但它让我第一次把 Controller、Service、Mapper、数据库、缓存和前端页面连成一条完整链路。

现在回头看，它更适合被定义为一个学习项目，而不是一个已经达到生产要求的教务平台。它的价值不在于功能规模，而在于让我从一个具体需求出发，理解一个 Web 应用是怎样从请求进入系统，再把结果返回给用户的。

## 项目定位

项目围绕一个简单的学生信息管理场景展开。管理员登录后，可以查询学生列表、按编号查询学生、添加学生、修改学生和删除学生。后端使用 Spring Boot 提供 Web 接口，前端是一个基于 Vue 3、Element Plus 和 Axios 的静态管理页面。

后端目前已经提供了完整的基础 CRUD 接口，前端页面主要完成了学生列表展示、刷新和删除操作，编辑交互仍然是后续需要补齐的部分。这样的完成度很符合它作为第一个项目的定位：先把核心链路跑通，再在后面的项目中补充更复杂的业务和工程能力。

## 技术栈与项目结构

项目使用 Java 17 和 Maven，主要技术包括 Spring Boot、Spring Web MVC、MyBatis、MySQL、Redis 和 Spring Security。代码按照基础的后端分层组织：

```text
src/main/java/com/example/studentsystem
├── config       # Security 和 Redis 配置
├── controller   # 学生管理接口
├── service      # 业务接口与实现
├── mapper       # MyBatis 数据访问接口
├── model/entity  # Student、User、Result 等实体
└── util         # 密码生成等辅助代码

src/main/resources
├── mapper       # StudentMapper、UserMapper XML
├── static       # 学生管理页面
└── application.yml
```

这次分层让我第一次意识到，目录结构不是为了把代码拆散，而是为了让不同职责有明确的归属。Controller 负责接收请求和返回结果，Service 负责组织业务流程，Mapper 负责和数据库交互，实体类则负责表达数据结构。

## 一次查询是怎么走完的

```text
浏览器请求 /student/list
  -> StudentController
  -> StudentService
  -> Redis 查询 students:all
  -> 未命中时调用 StudentMapper
  -> MySQL 查询 student 表
  -> 写入缓存并返回统一结果
```

查询全部学生时，Service 会先读取 Redis 中的 `students:all`。如果缓存没有命中，再通过 MyBatis 查询 MySQL，并把结果缓存 30 分钟。按编号查询时使用 `student:{id}` 作为缓存键。新增、修改和删除成功后，Service 会清理对应的详情缓存以及学生列表缓存，避免下一次读取到旧数据。

缓存是我在这个项目里第一次接触到的基础设施能力。虽然这里的缓存策略还比较简单，但它让我开始思考一个实际问题：数据更新之后，哪些缓存必须失效？如果只缓存查询结果，却没有处理更新场景，系统就可能出现数据库已经变化、页面仍然显示旧数据的情况。

## 登录认证是怎样接入的

项目使用 Spring Security 的表单登录流程。登录请求交给 Security 处理，用户信息通过 `UserDetailsService` 从 MySQL 查询，密码使用 BCrypt 进行校验。认证通过后，`/student/**` 接口才允许访问，退出登录则由 Security 负责处理。

这部分代码让我理解了认证和业务接口之间的关系：学生查询接口本身只负责处理学生数据，用户是否有资格访问接口由安全配置和认证上下文共同决定。虽然项目目前还没有展开复杂的角色权限控制，但已经具备了从数据库读取用户并完成基础认证的完整路径。

## 目前的不足

这个项目目前最大的不足，是“能运行”与“工程上足够完整”之间仍然有明显距离：

- 数据库和 Redis 配置还需要进一步改为环境变量管理，不能把环境相关信息直接写在配置文件中。
- 部分代码仍使用字段注入，后续会改为构造器注入，让依赖关系更清晰，也方便测试。
- 请求参数校验、统一异常处理和更明确的错误码还没有完善。
- 测试目前主要验证 Spring Boot 能否启动，真实的 Controller、Service 和缓存场景覆盖还不够。
- 前端的编辑和新增交互还没有完成，登录后的页面跳转也需要和前端路由重新统一设计。

这些问题并不意味着项目没有价值，反而说明它完成了一个重要的阶段性任务：把需要继续学习的地方暴露出来。对于第一个项目来说，知道哪里只是基础实现、哪里还没有达到工程要求，比简单地宣称“功能全部完成”更有意义。

## 它带给我的下一步

后来的 AI 面试助手开始补充完整产品闭环、JWT、SSE、Flyway、测试和云端部署；EventFlow 则进一步练习审核流、角色权限、事务一致性、防重复报名和名额并发控制。它们并不是和教务系统割裂的三个项目，而是沿着同一条学习路径逐步升级：先理解分层和数据访问，再理解产品交付，最后把业务规则和数据一致性放到更真实的场景里验证。

教务系统是这条路径的起点。它让我第一次完整走通了从页面请求到数据库的过程，也让我开始明白，项目经验不只是最后展示出来的页面，还包括对技术选择、实现边界和后续改进方向的清楚认识。

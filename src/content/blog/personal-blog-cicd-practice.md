“网站已经在本地打开”和“网站已经可以稳定发布”是两件不同的事。个人博客看起来只是一个静态页面，但一旦准备部署到已经运行着其他项目的服务器，就必须认真处理端口、容器、权限、密钥、上传、健康检查和公网访问。任何一项没有被验证，发布流程就可能停在一个看起来很模糊的状态。

这次博客部署采用了一个相对克制的方案：GitHub Actions 在 runner 上完成 Astro 构建，把静态产物和 Nginx 配置上传到服务器，再通过 Docker Compose 启动独立的 Nginx 容器。CI 和 CD 分开，CI 自动检查构建，CD 暂时手动触发。服务器不需要运行 Node.js 或数据库，也不需要提前保存博客 Git 仓库。

本文重点记录这套方案为什么这样设计、第一次发布遇到了什么问题，以及以后新增文章时怎样沿用同一套流程。文章中的命令和配置都围绕静态博客，不能直接复制成后端应用的生产方案，但其中的边界意识、故障定位和发布验证方法具有通用价值。

## 一、先明确 CI 和 CD 分别负责什么

CI 的任务是回答：“这个提交能不能被可靠地构建？”当前工作流在推送 `main` 和针对 `main` 的 Pull Request 上运行，执行依赖安装和 `pnpm build`。如果 frontmatter 错误、图片缺失、路由生成失败或 TypeScript 代码有问题，CI 会在合并前给出反馈。

CD 的任务是回答：“是否现在要把某个已经确认的版本发布到服务器？”当前 CD 使用 `workflow_dispatch`，需要在 GitHub Actions 页面手动运行。它不会因为任何一次分支提交自动改变生产环境，这给内容修改留下了检查和确认的空间。

两者分开并不是增加操作，而是把风险放在正确的边界。构建检查可以高频自动执行，生产发布则应该由人确认目标分支、站点 URL、部署端口和 SSH 配置都正确。未来如果发布频率和审批方式稳定，可以再把 CD 改成合并 `main` 后自动运行，但自动化的前提是发布链路已经有足够的失败保护。

## 二、服务器隔离：不能因为部署博客影响其他项目

目标服务器上已经运行两个项目，因此博客部署最重要的约束是“不影响现有服务”。我没有使用服务器上的全局 Compose 项目，也没有在脚本中执行 `docker compose down`。博客使用单独的项目名 `wybell-blog`，远程目录使用 `/home/ubuntu/wybell-blog`，容器和网络由这个 Compose 项目单独管理。

部署脚本只会处理自己的目录和容器：创建博客目录、上传静态文件、启动或更新 `wybell-blog`。它不会扫描并重建其他项目，也不会删除服务器上不属于博客目录的文件。这个边界比“我记得不要停止其他容器”更可靠，因为它被写进命令结构里。

## 三、为什么使用 Nginx 容器，而不是在服务器上直接运行开发服务

Astro 构建产物是静态文件，生产环境不需要 `astro dev`，也不需要常驻 Node.js。Nginx 负责读取 HTML、CSS、JavaScript、图片和字体文件，容器镜像使用 `nginx:1.27-alpine`，运行时资源占用很低。

Compose 中的关键映射是：

```yaml
services:
  blog:
    image: nginx:1.27-alpine
    ports:
      - "${BLOG_PORT:-8090}:80"
    volumes:
      - ./dist:/usr/share/nginx/html:ro
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
```

`dist` 以只读方式挂载，容器不需要修改构建产物。配置文件也只读挂载，Nginx 的行为可以被版本控制。生产服务因此变成“固定镜像 + 固定配置 + 静态目录”，问题边界比直接在服务器上安装和修改 Nginx 更容易复现。

## 四、端口选择是部署前检查，不是部署后猜测

第一次规划时曾准备使用 8085，但服务器检查发现现有项目已经使用了这个端口，虽然它绑定在 `127.0.0.1`，依然可能与 Docker 的端口绑定发生冲突。服务器的 80 和 8084 也已经被其他服务使用，因此博客最终选择 8090。

端口检查使用：

```bash
ss -lntp | grep -E ':(80|8084|8085|8090)\\b' || true
```

选择 8090 后，Compose 使用 `8090:80`，浏览器入口是服务器 IP 加 8090 端口。这个端口不会因为博客容器内部监听 80 就自动对公网可用，还必须同时满足 Docker 绑定、云防火墙和宿主机防火墙三个条件。

这里的经验是，端口不是某个项目可以随意占用的局部变量，而是服务器级共享资源。部署前先检查，远比容器启动失败后再从一堆日志中猜测冲突来源更省时间。

## 五、SSH 密钥：自动部署不能依赖交互式密码

GitHub Actions 运行在远程 runner 上，不能在上传时等待人工输入服务器密码，所以需要专用 SSH 密钥。密钥分为两部分：私钥保存在 GitHub Actions Secret，公钥放在服务器 `ubuntu` 用户的 `~/.ssh/authorized_keys` 中。

创建密钥时使用独立文件名，例如 `wybell-blog-deploy`，避免覆盖个人已有密钥。公钥可以放在服务器，私钥不能上传到服务器，也不能提交进 Git 仓库。工作流还使用 `DEPLOY_KNOWN_HOSTS` 固定服务器主机指纹，避免为了方便而使用关闭主机校验的参数。

Secret 和 Variable 的职责也要区分：

| 配置 | 类型 | 原因 |
| --- | --- | --- |
| `DEPLOY_SSH_PRIVATE_KEY` | Secret | 能够登录服务器，必须加密保存 |
| `DEPLOY_KNOWN_HOSTS` | Secret | 服务器主机身份信息，避免随意信任 |
| `DEPLOY_HOST`、`DEPLOY_USER`、`DEPLOY_PATH` | Secret | 属于部署连接配置，统一保护 |
| `PUBLIC_SITE_URL` | Variable | 构建时使用的公开站点地址 |
| `BLOG_PORT`、`DEPLOY_SSH_PORT` | Variable | 非敏感的端口配置 |

第一次配置时把三个公开变量误放在了错误位置，导致工作流在验证阶段提示缺少 `PUBLIC_SITE_URL`。这个失败没有连接服务器，说明“先校验配置，再执行网络操作”是有价值的。

## 六、工作流的具体发布链路

CD 工作流按以下顺序执行：

```text
Checkout main
    |
    v
校验 Secrets 和 Variables
    |
    v
安装 pnpm 与 Node.js
    |
    v
pnpm install --frozen-lockfile
    |
    v
pnpm build
    |
    v
准备 SSH 和 known_hosts
    |
    v
打包 dist.tar.gz
    |
    v
上传静态包、Compose 和 Nginx 配置
    |
    v
服务器解包并 compose up -d
    |
    v
容器内 healthz 检查
```

把构建放在上传前有两个好处：构建失败时不会触碰服务器；服务器只接收已经通过构建检查的产物。把 `docker compose up -d` 放在上传完成后，能够避免容器在文件尚未传完时读取半套静态资源。

## 七、上传超时：为什么构建成功仍然可能发布失败

第一次 CD 运行时，构建、打包和 SSH 准备都成功了，但上传步骤运行了接近 15 分钟后被取消。检查发现博客的 `dist` 目录包含多张较大的 PNG 图片，总体积接近 90MB。PNG 已经经过压缩，继续使用 tar.gz 并不会像压缩文本那样获得很大的缩小比例，因此真正的耗时来自网络传输。

这个问题不能简单归因于“GitHub Actions 不稳定”。发布流程需要知道产物大小、网络链路和合理的超时。随后我把 Job 总超时调整为 30 分钟，并给 SSH 增加：

```bash
-o ConnectTimeout=30
-o ServerAliveInterval=15
-o ServerAliveCountMax=20
```

同时给 SCP 设置 25 分钟的显式上限。连接超时负责处理根本连不上服务器的情况，保活负责让长时间传输的连接能够被检测，显式上限负责避免一个完全无响应的进程无限占用 runner。

更长期的解决方式仍然是优化资源：将适合的图片转换为 WebP 或 AVIF，按页面实际展示尺寸生成封面，删除不再使用的大文件，或者将大资源迁移到专门的对象存储。延长超时只能缓解当前网络问题，不能替代资源治理。

## 八、Docker 健康检查和公网验收是两回事

容器内健康检查访问 `http://127.0.0.1/healthz`，它可以确认 Nginx 进程启动、配置可以加载、健康路径能够返回 200。但这只覆盖容器内部，不代表宿主机端口映射和公网入口一定正常。

一次完整的验证应该分三层：

### 8.1 容器内部

检查容器状态和 Nginx 日志，确认容器没有反复重启。健康检查失败时先看挂载目录、配置语法和静态文件是否存在。

### 8.2 宿主机端口

在服务器执行：

```bash
ss -lntp | grep ':8090' || true
curl -I http://127.0.0.1:8090/
```

如果宿主机访问失败，重点检查 Docker 端口映射和服务器本机防火墙。

### 8.3 外部浏览器

最后从浏览器访问 `http://服务器IP:8090/`，检查首页、文章详情、图片、CSS、JavaScript 和内部链接。外部超时通常指向云防火墙或安全组；如果已经返回 502，则说明请求到达了某个入口，需要继续判断是云代理、宿主机 Nginx 还是 Docker 端口返回的响应。

这三层检查不能相互替代。容器内健康检查是发布脚本的硬门槛，浏览器验收则是用户体验的最后一层。

## 九、失败时如何定位，而不是直接重启所有服务

发布失败后，第一步应该看失败发生在哪个工作流步骤。配置校验失败不需要登录服务器；构建失败应该回到文章字段和资源路径；SSH 准备失败要检查私钥格式和 known hosts；上传失败要看连接、目标目录权限和文件体积；容器启动失败才进入 Docker 日志和 Compose 配置。

服务器上可以使用独立项目名检查：

```bash
docker compose -p wybell-blog -f /home/ubuntu/wybell-blog/docker-compose.yml ps
docker compose -p wybell-blog -f /home/ubuntu/wybell-blog/docker-compose.yml logs --tail=100 blog
```

不应该为了排查博客而执行全局 `docker compose down`，也不应该直接重启服务器。最小范围的诊断和恢复可以保护其他项目，也让故障原因更容易被复盘。

## 十、版本、合并和发布之间的关系

当前流程以 `main` 作为生产候选分支。开发分支的 Pull Request 会触发 CI，检查通过后合并到 `main`。合并本身不会自动触发 CD，生产发布仍然需要手动选择 `main` 运行工作流。

这意味着一次文章发布可以拆成三个明确状态：代码已经写在分支上，代码已经通过 CI 并合入 `main`，代码已经通过 CD 发布到服务器。每个状态都有不同证据，不应该把“GitHub 上有提交”直接当成“公网已经更新”。

手动 CD 还有一个实际好处：文章可以集中修改后一次发布，避免每次小修订都上传近 90MB 静态资源。等资源优化、回滚、域名和 HTTPS 等基础设施完善后，再考虑自动部署会更稳妥。

## 十一、回滚和后续改进

当前 CD 直接根据 `main` 最新提交构建并上传，适合项目早期，但还没有完整的历史版本目录和一键回滚。后续可以把产物按提交 SHA 保存到服务器，例如 `/home/ubuntu/wybell-blog/releases/<sha>/`，切换一个软链接指向目标版本，再通过 Compose 重启容器。这样可以在新版本异常时快速切回上一份已验证的静态文件。

还可以增加发布后的浏览器级检查，例如请求首页、RSS、sitemap 和一篇新文章，确认返回状态码与关键标题。对于纯静态站点，这种检查成本很低，却比只看容器 `Up` 更接近真实用户路径。

如果未来绑定域名，公网入口应该从 IP 加端口逐步迁移到 HTTPS 域名。届时需要重新配置 `PUBLIC_SITE_URL`、证书续期、Nginx server_name 和云防火墙规则。域名不是部署完成的前提，但应该被当作发布系统的下一阶段，而不是临时把 IP 写死在所有地方。

## 十二、一次发布应该留下什么证据

发布完成后，不能只保留“网页现在能打开”这一种模糊结论。至少应该记录发布的 Git 提交、Actions 运行编号、构建是否通过、服务器上的容器状态、对外端口、健康检查结果和浏览器验收时间。这样下一次出现问题时，可以先判断是代码变化、构建环境变化、服务器状态变化，还是网络入口变化。

对静态博客来说，最有价值的证据通常很简单：构建输出中生成了预期文章路径，服务器上的 `dist` 目录包含对应 HTML，容器使用了正确的只读挂载，`curl` 访问首页返回 200，浏览器能够加载 CSS 和封面。每一项证据都对应一段链路，缺少其中一项，就无法准确说明问题发生在哪里。

我还会把失败结果保留下来，而不是只记录成功发布。第一次上传超时、变量配置错误和公网 502 都是有效的工程信息。它们说明流程在什么阶段失败、哪些操作没有被执行、下一次应该先检查什么。只有把失败变成可检索的经验，CI/CD 才不只是一个按钮，而会逐步变成团队或个人可以信任的交付工具。

## 结语：可靠发布来自边界和证据

这次个人博客部署让我重新理解了 CI/CD。它不是在项目里放一个 YAML 文件就结束，也不是看到 Docker 容器运行就代表用户已经可以访问。可靠发布至少需要这些证据：构建成功、密钥校验通过、目标端口不冲突、静态包完整上传、独立容器正常运行、宿主机端口监听、云防火墙放行以及浏览器实际返回正确页面。

个人项目的规模虽然不大，但同样可以采用专业的工程习惯：用分支和 Pull Request 控制变更，用 CI 提前发现错误，用 CD 明确发布动作，用独立容器保护已有服务，用健康检查和分层验证确认结果。把这些步骤记录下来，下一次新增文章时就不需要重新猜测，也能更快定位真正的问题。

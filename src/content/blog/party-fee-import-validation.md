工单 1007930 的问题是“党费信息缴纳导入，没有校验到个人少交党费”。这个问题看起来像导入页面少了一条提示，实际影响的是缴费数据的准确性。如果系统只检查 Excel 文件能不能打开、金额能不能解析，却没有检查应缴金额和实缴金额之间的业务关系，那么少缴数据就可能直接进入正式表，继续影响后续统计、审核和报表。

这次问题的核心规则可以抽象成一句话：`实缴金额 >= 应缴金额`。实缴金额小于应缴金额时必须提示少缴并阻止数据通过校验；实缴金额等于应缴金额是正常情况；如果业务允许自愿多缴，实缴金额大于应缴金额则不应该被错误拦截。本文从导入链路出发，说明如何把这条规则放在正确位置，并让错误能够被准确定位、批次能够保持一致。

## 一、格式正确不代表业务正确

批量导入至少需要经过两层校验。第一层是格式校验，关注文件是否能被解析：文件是否为空，表头是否符合模板，人员编号和姓名是否为空，金额是否能够转换，日期格式是否正确。第二层是业务校验，关注解析出来的数据是否符合业务规则：人员是否存在，是否属于当前组织，应缴金额是否正确，实缴金额是否少于应缴金额，同一人员同一月份是否已经有缴费记录，当前数据是否允许修改。

例如下面的数据在 Excel 层面完全合法：

```text
姓名：张三
人员编号：P001
应缴党费：100.00
实缴党费：80.00
缴费月份：2026-07
```

它的每一列都有值，金额也都是合法数字，但业务上是不完整的，因为实缴金额少于应缴金额。此前的缺陷本质上就是把“文件可以读取”误当成了“数据可以入库”。导入模块必须在解析之后继续执行业务规则校验，不能在读取成功后直接进入保存逻辑。

校验顺序也很重要。金额格式解析失败时，不能继续拿一个空值参与比较；人员不存在时，不能继续用不存在的人员 ID 写入；组织范围不匹配时，不能因为当前操作人有导入权限就放过这条数据。每一行数据都应该经过可解释的校验阶段，并把结果保留下来。

## 二、金额比较必须使用 BigDecimal

金额不能使用 `double` 或 `float` 做核心业务比较：

```java
double payable = 100.10;
double actual = 100.00;
```

二进制浮点数无法精确表示所有十进制小数，经过运算后可能出现看起来很小但会影响边界判断的精度误差。党费金额虽然通常保留两位小数，但“刚好相等”和“刚好少一分钱”都必须得到确定结果，因此应使用 `BigDecimal`。

```java
BigDecimal payable = new BigDecimal("100.00");
BigDecimal actual = new BigDecimal("80.00");

if (actual.compareTo(payable) < 0) {
    throw new BusinessException("实缴金额不能少于应缴金额");
}
```

`compareTo` 返回小于 0 表示实缴金额更小，等于 0 表示两者相等，大于 0 表示实缴金额更多。判断少缴时只需要拦截 `< 0`，不能用 `equals` 判断，因为 `100.0` 和 `100.00` 在 `BigDecimal.equals` 中可能因为 scale 不同而不相等，但从金额业务上它们是相同的。

```java
// 不建议：先转换成浮点数再比较
if (actual.doubleValue() < payable.doubleValue()) {
    // 可能出现精度边界问题
}

// 建议：直接使用 BigDecimal 的数值比较
if (actual.compareTo(payable) < 0) {
    addError(row, "实缴金额少于应缴金额");
}
```

金额解析还要统一输入规则。空值、负数、带逗号的字符串、货币符号、小数位超过两位，都应当得到明确错误。是否允许把 `1,000.00` 清洗成 `1000.00`，要以导入模板约定为准，不能在不同入口采用不同规则。数据库金额字段也应使用定点数类型，例如 `DECIMAL(12, 2)`，避免 Java 层和数据库层使用不同精度。

## 三、把导入流程拆成可观察的阶段

一个可靠的导入流程可以拆为以下阶段：

```text
上传文件
   |
   v
读取文件和表头
   |
   v
解析每一行
   |
   v
格式校验
   |
   v
查询人员和组织基础数据
   |
   v
业务规则校验
   |
   v
汇总全部错误
   |
   +---- 有错误：返回明细，不写入正式表
   |
   +---- 无错误：事务内批量保存
```

代码层面可以把“校验”与“保存”分成两个方法，避免在循环中校验一行就立刻插入一行：

```java
public ImportResult validateRows(
        List<FeeImportRow> rows,
        Long organizationId) {
    List<ImportError> errors = new ArrayList<>();

    for (int i = 0; i < rows.size(); i++) {
        FeeImportRow row = rows.get(i);
        int line = i + 2; // 第一行为表头

        if (row.getEmployeeNo() == null
                || row.getEmployeeNo().isBlank()) {
            errors.add(new ImportError(line, "employeeNo", "人员编号不能为空"));
            continue;
        }

        BigDecimal payable = parseAmount(
                row.getPayableAmount(), line, errors);
        BigDecimal actual = parseAmount(
                row.getActualAmount(), line, errors);
        if (payable == null || actual == null) {
            continue;
        }

        if (actual.compareTo(payable) < 0) {
            errors.add(new ImportError(
                    line, "actualAmount", "实缴金额不能少于应缴金额"));
        }

        checkPersonScope(row, organizationId, errors);
        checkDuplicate(row, errors);
    }

    return new ImportResult(errors);
}
```

发现错误后不应该立刻抛出一个“导入失败”就结束。批量文件可能同时存在第 3 行少缴、第 8 行人员不存在、第 15 行重复数据，用户需要一次看到所有问题，而不是改完第一处后重新上传，才能发现下一处。错误结构至少应包含行号、字段和消息：

```json
{
  "success": false,
  "total": 20,
  "errorCount": 2,
  "errors": [
    {
      "rowNumber": 8,
      "field": "actualAmount",
      "message": "实缴金额不能少于应缴金额"
    },
    {
      "rowNumber": 12,
      "field": "employeeNo",
      "message": "人员编号不存在"
    }
  ]
}
```

前端拿到行号和字段后，可以在错误列表中定位原始数据，也可以在导入预览中标记对应单元格。这样错误信息就从日志里的技术异常，变成了用户可以实际修复的业务反馈。

## 四、全量校验通过后再写入

涉及缴费金额的数据，更适合采用“全量校验，全部通过后再写入”的策略。只要一个批次中存在少缴、人员不存在、组织不匹配或重复数据，整个批次都不进入正式表，并返回全部错误明细。这样用户能够明确知道这次导入没有产生任何正式数据，不会出现一部分保存成功、另一部分失败但页面没有说清楚的情况。

如果业务确实要求允许部分成功，也必须返回成功数量、失败数量、批次号和失败行明细，并且为成功数据建立可追踪的导入批次。不能让用户只看到一个“处理完成”，却不知道到底有多少数据写入。

校验通过后的保存过程要放在事务中：

```java
@Transactional
public void saveImport(
        List<FeeImportRow> rows,
        Long operatorId) {
    for (FeeImportRow row : rows) {
        FeePayment payment = convert(row, operatorId);
        feePaymentMapper.insert(payment);
    }
}
```

如果第 15 条保存失败，事务应回滚前面已经插入的记录，避免正式表出现半个批次。事务并不能替代前置校验：它只能保证这一批写入要么全部成功、要么全部回滚，不能保证业务规则自动正确。少缴规则仍然必须在正式写入前明确执行。

## 五、重复导入和数据库约束

同一组织、同一人员、同一月份通常不应出现多条缴费记录，可以在数据库建立联合唯一约束：

```sql
UNIQUE KEY uk_fee_payment_person_month
(
    organization_id,
    employee_id,
    payment_month
)
```

应用层可以在预校验阶段查询重复数据，给用户更友好的错误；数据库约束则是最后一道防线，防止并发请求或绕过页面的接口写入重复记录。应用层先查、数据库后约束不是重复建设，而是分别承担体验和正确性。

如果业务允许重新导入覆盖旧数据，必须明确覆盖策略：是更新实缴金额，还是创建修正记录；谁可以覆盖，覆盖后是否留下变更日志；已进入审核流程的数据能不能覆盖。不能简单地把唯一键异常转换成“导入失败”，也不能为了让接口成功而无条件覆盖历史。

## 六、边界场景和回归测试

这次缺陷的回归重点不是“页面有没有提示”，而是“少缴数据最终没有进入正式表”。至少要测试：

- 实缴金额小于应缴金额时，返回少缴错误，数据库没有新增记录。
- 实缴金额等于应缴金额时，导入成功。
- 实缴金额大于应缴金额时，按照业务规则允许通过。
- 应缴金额或实缴金额为空、格式错误、为负数时，返回对应字段错误。
- 金额精确到两位小数，以及刚好相差 0.01 的边界情况。
- 一批数据中只有一条少缴和多条少缴时，全部错误都能返回。
- 人员不存在、人员不属于当前组织、同一人员同一月份重复时，错误行号正确。
- 只要批次校验失败，正式表不写入任何一条数据。
- 批量保存中途发生数据库异常时，事务回滚，不留下半个批次。
- 并发导入同一人员同一月份数据时，联合唯一约束能够阻止重复。

还应检查导入日志或批次记录，确认操作人、导入时间、文件来源和结果能够被追踪。对于金额类业务，日志不是可有可无的调试信息，而是出现数据争议时的重要证据。

## 七、这次修复的工程价值

这个 BUG 让我认识到，批量导入绝不是一个简单的文件上传功能。它同时涉及文件格式、字段类型、金额精度、业务规则、组织数据权限、重复数据、错误反馈、事务、批量性能和结果追踪。

修复少缴校验时，真正重要的不是增加一个 `if`，而是把业务规则放在正确的校验阶段，使用 `BigDecimal` 做可靠比较，先汇总错误再决定是否入库，用事务保证批次一致，用数据库约束防止并发重复，并通过回归测试验证异常数据确实不会进入正式表。只有这样，导入功能才从“文件能读”提升为“业务数据可以被信任”。

## 八、修复落地时还要关注性能和可追踪性

如果导入文件包含几千行甚至更多数据，不能在循环中对每一行都单独查询人员和历史缴费记录，否则很容易形成大量重复 SQL。更合理的做法是先收集所有人员编号和缴费月份，批量查询基础数据，再放入内存 Map 中进行匹配；对数据库已有记录也可以按组织、人员集合和月份集合批量查询。这样既减少网络往返，也能让校验逻辑更容易测试。

批量查询不能牺牲数据权限。查询人员时仍然要带上当前组织范围，不能因为做了批处理就扩大操作人可见的数据。对于很大的文件，还应限制单次上传大小和最大行数，避免一次请求占用过多内存；必要时采用分段解析，但“先全部校验再写入”的业务语义仍然要保持清楚。

导入结果最好生成批次记录，保存操作人、文件名或文件摘要、总行数、成功数、错误数、处理时间和最终状态。这样当用户问“这次文件到底有没有导入”时，可以根据批次号回答，而不是依赖服务日志猜测。金额类数据发生修正时，还应保留原始值、修正值和操作原因，避免只看到最后金额却无法解释变化来源。

最后，错误消息需要区分用户可修复错误和系统异常。少缴、人员不存在、格式错误属于用户可以修改的导入错误，应返回结构化明细；数据库连接失败、事务异常属于系统错误，应记录完整日志并提示稍后重试，不能把堆栈信息直接返回给用户。校验、保存、结果记录和监控共同组成了导入功能的交付闭环。

在修复完成后，还要确认应缴金额的来源是可信的。它可能来自人员类别、缴费比例、工资基数或某个已经生成的应缴计划，不能只把导入文件里的“应缴金额”当成唯一标准。如果文件中的应缴金额可以被操作人任意修改，系统即使正确判断了“实缴不少于应缴”，也可能放过被人为降低的应缴数据。更稳妥的方式是根据人员和月份查询系统计算出的应缴金额，导入文件只提供实缴金额，或者至少对两者不一致给出单独提示。

还应明确补缴、减免和特殊人员的例外规则。某些月份可能存在减免、补缴或调整记录，不能简单地把所有小于标准金额的数据都当作错误。例外必须有明确的业务状态、审批依据和可追踪记录，不能通过在校验代码中增加一个难以理解的人员名单来绕过规则。规则越接近金额业务核心，越需要用命名清晰的策略和测试数据表达，而不是依赖隐含约定。

因此，这次修复的最终验收不止是补上少缴提示，还包括确认标准金额来源、明确例外政策、验证数据库最终结果和保留导入证据。只有业务规则、技术校验和后续审计三者一致，导入数据才真正具备可用性和可信度。

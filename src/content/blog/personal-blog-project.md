一个个人博客看起来像是最容易开始的项目：准备一个首页，放几张卡片，写几篇文章，再部署到服务器上就完成了。但真正把它做成一个可以持续使用的站点之后，我才发现，博客并不是“把文字显示出来”这么简单。它同时包含内容管理、页面结构、文章路由、图片资源、元数据、搜索引擎入口、版本管理、发布流程和运行维护等多个问题。任何一个环节没有被认真设计，后续新增文章时都可能需要手工改页面，甚至因为一个封面或一条链接导致构建失败。

这个项目是我的个人博客，站点名称是“Wybell空间”。它的目标不是做一个追求复杂交互的内容平台，而是把我做过的项目、学习过程、工作经历、生活记录和阶段性思考整理成一套稳定的个人知识入口。站点目前使用 Astro 生成静态页面，文章使用 Markdown 保存，内容通过 Astro Content Collections 进行校验，生产环境使用 Nginx 容器提供静态文件服务，代码经过 GitHub Actions 构建和手动 CD 发布。

本文会以这个博客本身为例，从需求分析开始，完整说明我为什么选择静态站点、怎样组织文章数据、如何让文章卡片和详情页使用同一份内容、怎样控制布局稳定性，以及第一次部署时遇到的端口、上传超时和云防火墙问题。文章中的重点不是罗列技术名词，而是说明每个选择解决了什么问题，哪些能力已经真正完成，哪些边界仍然需要继续补充。

## 一、先定义博客要解决的问题

### 1.1 它首先是一个长期记录工具

我没有把这个项目定义成一个需要登录、后台编辑、即时发布的内容管理系统。对我当前的使用场景来说，最重要的能力是：文章可以在本地编辑，修改可以被 Git 清楚记录，构建过程可以提前发现错误，发布过程可以重复执行，线上页面可以被稳定访问。

这意味着博客的第一优先级不是后台功能数量，而是内容的可维护性和发布的可解释性。新增一篇文章时，我希望只需要增加一个 Markdown 文件和必要的图片，然后运行构建检查；不希望再手动修改首页数组、文章列表页面和站点地图。文章的标题、日期、分类、封面和标签应该属于文章自身，而不是散落在多个组件里。

### 1.2 内容分区必须与实际写作习惯对应

站点目前把内容分成四个主要方向：技术空间、生活空间、随想录和关于我。技术空间内部又分为项目实践、技术学习、技术栈、工程实践和工作经历。这样的分区不是为了让导航看起来丰富，而是为了区分不同类型的内容：项目实践回答“我做过什么系统”，技术学习回答“我理解了什么技术问题”，工程实践回答“怎样让功能可靠地交付”，工作经历则记录真实工作中的业务和协作经验。

如果所有文章都只放在一个时间线里，读者很难判断一篇文章是在讲项目背景、技术原理，还是线上问题。反过来，如果分类太细，每次写文章又要纠结应该放在哪个栏目，内容也会失去连续性。因此我把分类收敛到稳定的业务语义，并让分类值进入内容 schema，避免页面和文章之间出现拼写不一致。

### 1.3 卡片布局需要稳定，内容更新不应该改变页面骨架

这个项目在开发过程中反复遇到一个问题：长标题、长摘要或者不同尺寸的图片会让某些卡片比旁边的卡片更高，页面因此出现明显的错位。文章内容应该可以自由增长，但卡片作为导航入口需要有稳定的视觉边界。于是我把“固定卡片结构”和“可变文章内容”明确分开：文章详情页可以展示完整内容，文章列表卡片只展示封面、标题、摘要、日期和标签；图片使用固定的展示区域，文字超出时由组件自身处理，不让整页布局跟着一篇文章任意拉长。

这也是我后来坚持的一个项目原则：除非明确提出布局调整，否则新增文章、替换文章正文或修改文章摘要，都不应该改变已有页面的尺寸关系。内容是数据，布局是组件契约，两者不能互相牵着走。

## 二、技术选型：为什么使用 Astro 静态站点

### 2.1 静态内容不需要常驻后端

博客的主要数据是文章正文和图片，访问者以读取为主，没有复杂的实时写操作。使用 Astro 的静态输出模式，可以在构建阶段把 Markdown 文章渲染成 HTML，生产环境只需要一个 Nginx 容器。这样运行时不需要 Node.js 进程，不需要数据库，也不需要为每次访问重新执行模板渲染。

静态站点的另一个优点是运行边界清楚。构建失败发生在 GitHub Actions，页面错误可以在部署前发现；服务器只负责提供已经生成的文件，线上问题不会因为某个 Node 进程内存泄漏或数据库连接池耗尽而变得复杂。对于个人博客这种访问量有限、内容变更频率可控的站点，这个取舍比为了使用动态服务端渲染而引入完整后端更合适。

### 2.2 Astro 负责页面组装，Markdown 负责内容表达

项目中的 Astro 页面负责布局、导航、数据筛选和路由生成，Markdown 文件负责文章的标题、摘要、日期、分类、封面、标签和正文。组件不需要知道每篇文章的具体内容，只需要接收一条经过 schema 校验的文章记录。

这种分工让我可以在不触碰页面组件的情况下新增文章。例如新增加一篇技术学习文章，只需要在 `src/content/blog/` 添加文件，把 `section` 设置为 `learning`，文章会自动进入技术学习列表，并被文章详情路由、RSS、站点地图和首页相关内容读取。组件不需要增加一条 `if`，这正是内容驱动页面相对于手写页面数组的价值。

### 2.3 TypeScript 和 pnpm 负责构建基础

项目使用 TypeScript 编写 Astro 配置、页面逻辑和站点配置，使用 pnpm 管理依赖。生产构建通过 `pnpm build` 执行，生成结果位于 `dist/`。依赖安装使用 `pnpm install --frozen-lockfile`，确保 CI 使用锁定版本，不会因为某次重新解析依赖而产生本地和线上构建结果不一致。

这里的 TypeScript 不只是为了给组件添加类型提示。文章集合、项目配置、导航配置和技术栈数据都通过类型或 schema 约束，减少了“字段改了一个地方，另一个页面运行时才报错”的情况。对一个持续维护的个人项目来说，早一点在构建阶段暴露错误，成本远低于线上访问时才发现链接或字段失效。

## 三、内容模型：把文章当成结构化数据

### 3.1 文章 frontmatter 的字段设计

博客文章的基本字段如下：

| 字段 | 作用 | 约束或说明 |
| --- | --- | --- |
| `title` | 文章标题 | 必填字符串，出现在卡片和详情页标题中 |
| `description` | 摘要 | 必填字符串，作为卡片摘要和页面描述 |
| `pubDate` | 发布时间 | 必填日期，用于排序和 RSS |
| `updatedDate` | 修改时间 | 可选，用于文章详情页展示 |
| `section` | 技术分区 | `learning`、`practice`、`project` 或 `experience` |
| `projectSlug` | 所属项目 | 可选，用于项目详情页关联文章 |
| `cover` | 封面路径 | 可选，指向 `public/` 下的资源 |
| `coverAlt` | 封面替代文本 | 可选，补充图片语义 |
| `tags` | 技术标签 | 字符串数组，用于卡片展示 |
| `draft` | 是否草稿 | 草稿不会进入公开列表 |

这些字段解决了几个实际问题。首先，页面不需要解析正文的第一段来获得摘要，摘要可以根据卡片空间单独控制。其次，文章所属分区是明确的枚举值，不会出现 `practice`、`Practise` 和“工程实践”混在一起。最后，封面路径和替代文本同时存在，既保证视觉展示，也不牺牲可访问性。

### 3.2 schema 把错误挡在构建之前

在 `src/content.config.ts` 中，博客集合使用 Astro 的 `defineCollection` 和 Zod schema 定义字段类型。文章缺少标题、日期或分区时，构建阶段会直接失败。日期由 `z.coerce.date()` 统一转换，页面不需要在每个地方重复处理字符串日期。

schema 并不能替代写作判断。它只能保证字段存在、类型正确和分区值合法，不能判断一篇文章是否真的写清楚了问题，也不能判断封面是否与正文相关。但它可以消灭一类低级错误：把日期写成无法解析的格式、把标签写成字符串而不是数组、把分区拼错导致文章从列表中消失。工程质量往往就是从减少这些低级错误开始的。

### 3.3 内容集合统一服务多个入口

同一条文章数据会被多个页面使用：技术分区列表读取标题和摘要，文章详情页调用 `render` 渲染 Markdown，首页读取最近文章，RSS 使用标题、描述和链接，sitemap 使用文章路径，站点统计使用文章集合数量。这样做的好处是单一事实源，代价是新增字段时需要检查所有消费者是否兼容。

我没有在每个页面里直接写自己的文章排序规则，而是把技术文章的读取和分页集中到 `src/lib/technical.ts`。它负责过滤草稿、按发布时间倒序和计算分页。页面只关心当前分区和当前页的数据。将数据筛选从页面中抽出来之后，文章排序规则变得一致，后续调整每页数量也只需要修改一个位置。

## 四、路由与文章体验：列表、卡片和详情页使用同一条链路

### 4.1 静态路径在构建阶段生成

文章详情页使用动态路由，构建时通过 `getStaticPaths` 为每篇文章生成路径。路径不会在访问时临时创建，而是在构建阶段确定下来。技术文章的路径类似 `/posts/personal-blog-project/`，具体地址由文件名和路由规则共同决定。

动态路由的关键不是“能不能打开一篇文章”，而是新增文章以后是否会自动产生正确页面。当前流程是：集合加载文件，路由读取集合条目，渲染器生成正文，布局组件负责标题、更新时间、目录和上一篇/下一篇导航。文章文件本身不需要写 URL，也不需要在路由文件中新增映射。

### 4.2 卡片不是正文的缩小版

技术文章卡片使用封面、分区标签、标题、描述、日期和标签作为导航信息。它不会把正文前几百字直接塞进卡片，因为正文段落通常没有为固定高度设计，直接截取还可能在句子中间断开。摘要是文章作者主动提供的入口文案，它应该告诉读者文章解决什么问题，而不是复制正文。

卡片点击后进入文章详情页，详情页再展示完整标题、封面、目录、正文和文章导航。列表和详情共享同一条文章数据，但使用不同的视觉组件。这样可以保持卡片长度固定，也可以让文章在详情页充分展开，而不需要为了适应卡片而牺牲文章表达。

### 4.3 目录和字数统计属于阅读辅助

文章详情页从 Markdown 渲染结果中读取 headings，生成目录。文章正文中的代码块、链接标记和图片语法不会被当作普通中文内容计算，字数统计会对正文进行清理后再统计中文字符和英文单词。这个统计不是为了制造阅读压力，而是让文章长度和信息量更可见，也帮助我检查“专业长文”是否真的达到预期长度，而不是只看页面滚动距离。

## 五、封面和静态资源：图片也是内容的一部分

### 5.1 封面路径要稳定

项目把图片放在 `public/` 目录，文章 frontmatter 使用以 `/` 开头的公开路径。例如项目实践文章使用 `/project-personal-blog.png`，技术学习文章使用 `/cover-learning-blog.png`，工程实践文章使用 `/cover-practice-blog-deployment.png`。构建时这些文件会被原样复制到输出目录，文章页面和卡片都通过同一个 URL 读取。

这种方式适合个人博客，因为图片不需要经过复杂的上传服务。它的注意点是文件名要稳定、大小要可接受、替换图片时要保留路径或同步修改所有引用。如果文件只放在本地临时目录而没有复制进仓库，CI 在 GitHub runner 上构建时一定找不到它，这是本地能看、线上失败的典型问题。

### 5.2 替代文本不能省略

封面不是纯装饰时，`coverAlt` 应该说明图片表达的内容。文章卡片中的图片使用懒加载，详情页根据文章重要性决定加载策略。图片如果加载失败，标题和摘要仍然必须可以独立表达文章入口，不能把关键内容只放在图片里。

### 5.3 资源体积会影响发布速度

本次博客的静态输出包含多张 PNG 图片，构建后的 `dist` 体积接近 90MB。PNG 本身已经经过压缩，继续使用 tar.gz 并不会大幅缩小体积，所以第一次通过 SSH 上传时花费了较长时间。这个问题让我认识到，静态站点虽然运行时轻量，但资源管理仍然会直接影响发布速度。后续可以通过 WebP 或 AVIF、合适的图片尺寸、页面实际展示尺寸和资源清理来降低发布包大小。

## 六、站点配置和页面布局的边界

### 6.1 项目数据与文章数据是两层模型

文章集合描述具体文章，`site.config.ts` 中的 `projects` 描述项目目录。个人博客作为一个项目，需要同时拥有项目条目和项目实践文章：项目条目负责项目实践页面中的卡片、技术栈、角色和状态，文章负责进入详情后的完整复盘。通过 `projectSlug: personal-blog` 将两层数据关联起来，项目详情路由可以找到对应文章。

这比把整篇文章直接写进项目配置更合理。配置文件适合放短摘要和导航数据，Markdown 适合放长文本和代码。随着文章变长，如果把正文塞进 TypeScript 数组，编辑体验、代码可读性和 Markdown 渲染都会变差。

### 6.2 固定布局是一种组件契约

博客的布局不是由文章内容“推导”出来的，而是由组件和 CSS 共同定义的。页面区域有明确的网格、间距、图片展示比例和卡片结构。新增文章会改变列表中的数据数量，但不会改动卡片的固定高度、栏目顺序和首页骨架。

这套边界对持续更新非常重要。文章标题可能变长，封面尺寸可能不同，标签数量也可能增加，但组件要通过截断、换行、固定图片区域和稳定网格来承受这些变化。内容作者不应该因为担心破坏页面而把文章标题写得不自然，页面组件也不应该因为一篇文章很长就改变所有卡片的尺寸。

### 6.3 首页只选择必要的精选项目

技术空间可以展示全部项目，但首页的精选项目区域只选择最适合首页入口的项目。个人博客作为新项目加入技术项目目录，不会自动挤进首页精选区域，也不会改变首页原有的两张精选项目卡片。这个过滤是有意的：内容完整性和首页视觉密度不是同一个问题。

## 七、从文章生成搜索入口

### 7.1 sitemap 不应该手工维护

站点地图根据页面和文章集合生成，技术、生活、随想的文章路径都会被纳入。新增文章只要通过 schema 和构建，它就能进入 sitemap。手工维护 XML 的方式很容易漏掉新文章，也容易在文章重命名后留下旧地址。

### 7.2 RSS 面向持续订阅

RSS 使用文章的标题、摘要、发布日期和文章链接生成条目。这里同样读取内容集合，而不是另外维护一份“最近文章”数组。文章更新日期和发布时间的含义要区分：发布时间表示文章第一次公开，更新时间表示内容确实发生过修改，不能每次构建都无意义地改变更新时间。

### 7.3 robots.txt 使用动态页面

robots.txt 由 Astro 页面生成，站点 URL 通过 `PUBLIC_SITE_URL` 环境变量配置。开发环境没有正式域名时可以使用默认值，但生产构建必须提供实际访问地址，否则 sitemap 的绝对链接会指向占位域名。这个设置也说明静态站点并不代表所有内容都应该硬编码，适度的构建时环境配置仍然必要。

## 八、CI/CD：把发布动作拆成可验证的步骤

### 8.1 CI 只负责证明代码能构建

当前 CI 在推送 `main` 和针对 `main` 的 Pull Request 上运行，核心步骤是安装锁定依赖并执行 `pnpm build`。它不登录服务器，也不改变生产环境。这样做的好处是 Pull Request 在合并之前就能发现 frontmatter 错误、图片缺失、路由生成失败和 TypeScript 构建问题。

CI 通过并不等于网站已经上线，它只证明当前提交可以生成静态站点。这个边界必须保持清楚，否则一旦把部署和构建混在一个自动流程里，任何一次普通提交都可能直接改变生产页面。

### 8.2 CD 通过人工触发控制生产发布

CD 使用 GitHub Actions 的 `workflow_dispatch`，由我在确认变量、密钥和目标分支后手动执行。工作流会在 GitHub runner 上重新检出代码、构建 Astro 站点、打包 `dist`，然后通过 SSH 上传 `dist.tar.gz`、Compose 文件和 Nginx 配置。

服务器不需要事先 clone 博客仓库。远程目录由工作流创建，静态文件解包后由独立的 `wybell-blog` Compose 项目启动 Nginx 容器。这样服务器只保存运行所需的输出文件和部署配置，不承担代码仓库管理职责。

### 8.3 为什么使用独立 Compose 项目

服务器上已经有其他项目运行，因此博客不能使用全局的 `docker compose down`，也不能依赖现有项目的默认目录和网络。工作流固定使用 `docker compose -p wybell-blog`，容器、网络和项目名称都与其他系统隔离。发布时只执行这个项目的 `compose up -d`，不会停止或重建其他 Compose 项目。

端口也经过实际检查。服务器已有项目占用了 80、8084，以及本机回环地址上的 8085。博客最终使用 8090 映射容器的 80 端口：

```text
服务器 8090 -> wybell-blog 容器 80 -> Nginx 静态文件
```

端口选择不是随意填写的部署参数，而是必须结合服务器现状确认的资源边界。

## 九、第一次部署中暴露的问题

### 9.1 Actions 变量和环境名称不是一回事

第一次运行 CD 时，配置校验提示缺少 `PUBLIC_SITE_URL`。原因不是代码，也不是 SSH，而是把三个变量的内容放到了错误的配置位置。GitHub Actions 的 `vars.PUBLIC_SITE_URL` 必须对应一个独立变量，名称和值不能拼在一个环境名称里。

这个问题值得记录，因为配置页面中的“Environment”和“Variables”容易让人混淆。Secrets 用于 SSH 私钥、服务器地址、部署用户和 known hosts；Variables 用于站点 URL、端口等不需要加密的构建参数。工作流启动后先校验这些值，可以让错误在连接服务器之前暴露，避免执行到一半才发现参数缺失。

### 9.2 大文件上传需要合理的超时和保活

静态输出接近 90MB，第一次上传步骤运行了 15 分钟后被取消。构建并没有失败，SSH 密钥也没有问题，真正耗时的是 GitHub runner 到服务器之间的 SCP 传输。为此我把工作流整体超时时间从 15 分钟延长到 30 分钟，并给 SSH 设置连接超时、ServerAliveInterval 和 ServerAliveCountMax，同时为 SCP 增加 25 分钟的显式等待上限。

这不是无限延长等待时间，而是让慢网络下的正常传输有机会完成，同时在真正没有响应时能够明确失败。后续如果资源继续增长，还需要从图片格式、资源尺寸、发布缓存或对象存储等方向解决根本问题，而不是不断把超时改得更大。

### 9.3 云防火墙放行后仍要区分 502 和超时

部署成功后，浏览器最初无法访问 8090。放行云防火墙之后，访问从连接超时变成 HTTP 502，这说明请求已经到达服务器，但需要继续检查宿主机端口、Docker 端口映射和其他代理。容器内部的 `/healthz` 检查只能证明 Nginx 容器内的服务正常，不能完全证明公网入口可用。

因此一次完整的发布验证至少要分三层：容器内部请求、服务器宿主机请求、外部浏览器请求。三层结果不同，排查方向也不同：容器内失败看 Nginx 配置和挂载目录；宿主机失败看端口映射和容器状态；只有外部失败时才重点检查云防火墙、安全组和宿主机防火墙。

## 十、测试和验收：构建成功只是起点

### 10.1 构建验收

每次内容变更至少执行 `pnpm build`。构建会检查 frontmatter、静态路由、组件类型和资源引用。文章新增后还要确认生成的文章 HTML、栏目列表、RSS、sitemap 和 robots 页面都存在。

### 10.2 链接和文章入口验收

链接检查不能只打开首页。需要抽查技术空间、项目详情、学习文章、工程实践文章、生活文章和随想文章，并确认卡片点击后进入对应详情页。文章的上一篇、下一篇导航也要检查，尤其是新增文章日期靠前时，排序可能改变导航关系。

### 10.3 线上验收

发布后先查看容器状态和端口：

```bash
docker ps --filter "label=com.docker.compose.project=wybell-blog"
ss -lntp | grep ':8090' || true
curl -I http://127.0.0.1:8090/
```

然后在浏览器中检查首页、技术空间、三篇新文章、图片加载、文章内部链接和移动端基本展示。对于静态博客来说，容器显示 `Up` 只是进程存活，不代表图片挂载正确、路由完整或公网入口真的可用。

## 十一、内容更新的实际工作流

以后新增文章的流程可以保持很简单：

1. 在 `src/content/blog/` 新建 Markdown 文件。
2. 填写标题、描述、日期、分区、封面和标签。
3. 把图片放进 `public/`，确认 frontmatter 路径和文件名一致。
4. 在本地阅读文章，检查标题层级、代码块和链接。
5. 执行 `pnpm build`，修复所有构建错误。
6. 本地提交并推送到分支，创建或更新 Pull Request。
7. CI 通过后合并到 `main`。
8. 需要上线时再手动运行 CD，并检查线上入口。

这个流程把“写内容”和“改变生产环境”分成了两个阶段。文章可以先在分支上整理，CI 负责验证，合并代表进入稳定版本，CD 的手动操作代表我明确确认要发布。对于个人项目来说，这套流程已经足够清晰，也为以后自动化部署留下了改造空间。

## 十二、当前边界和后续计划

这个博客已经能够完成文章管理、静态生成、项目关联、RSS、sitemap、Docker 运行和手动发布，但它还不是一个完整的内容平台。当前没有后台编辑器、登录系统、评论系统、全文搜索和文章草稿在线预览。草稿通过 frontmatter 的 `draft` 字段控制，内容修改依赖本地 Git 工作流。

后续可以考虑增加文章全文搜索、构建产物缓存、图片自动压缩、旧链接重定向和更完善的发布回滚。搜索需要先明确是否接受浏览器端加载索引，图片优化需要明确质量和存储成本，自动发布需要补充生产审批和失败回滚策略。功能不是越多越好，只有当新增能力能够减少维护成本或改善真实使用体验时，才值得加入。

## 结语：个人项目也要有交付意识

这个博客对我来说最重要的收获，不是完成了一个可以展示文章的页面，而是开始用系统的方式处理一个看似简单的项目。内容需要模型，页面需要边界，图片需要资源管理，文章需要可追踪的版本，发布需要独立的环境，线上问题需要分层验证。

当我把一篇文章写进 Markdown 时，它不只是文本；当它通过 schema、构建、CI、Docker 和浏览器验收之后，才真正变成一个可以被访问、被维护、被继续更新的站点内容。这个过程也提醒我，工程实践并不只存在于大型团队。只要一个项目会持续使用，就值得把需求、边界、失败路径和发布方式记录清楚。

## 第一章：起点——从“背代码”到“拆代码”

最初接触算法时，我犯了一个几乎所有初学者都会犯的错误：背代码。面对一道题，我的第一反应是“这道题的题解怎么写”，而不是“这道题的本质是什么”。

### 1.1 第一次“顿悟”：看懂三数之和

三数之和是我花时间最长、也最痛苦的题之一。那时候我不知道什么是“双指针”，不知道什么是“去重逻辑”。我只知道：先排序，然后固定一个数，再用两个指针找另外两个数。

当时我的状态是这样的：能看懂代码的每一行，但看不懂为什么这样写。我不理解为什么 `if (i > 0 && nums[i] == nums[i-1]) continue;` 这行代码能去重，不理解为什么左指针和右指针要同时移动。

转折点出现在一个深夜。我在纸上画了一个数组 `[-4, -1, -1, 0, 1, 2]`，然后手动模拟了一遍程序执行的轨迹。那一刻我发现：所谓“去重”，其实是在“生成组合”的过程中，人为地屏蔽了“从相同的数字出发”这个可能性。`i > 0` 保证了第一个数字不会漏解，`nums[i] == nums[i-1]` 保证了重复起点的分支不会被重复遍历。

我学到的第一课：算法代码的本质是“规则的精确表达”。每一行代码都对应着一个具体的决策规则。看懂代码不等于理解算法，只有能用自然语言把每一步的决策逻辑说出来，才算真正掌握了。

### 1.2 从“三数之和”到“双指针”的抽象

做完三数之和后，我回头看“两数之和”，发现可以用暴力法也可以用哈希表。我意识到，“双指针”这种模式适用于“有序数组中寻找满足特定条件的数对”，而“哈希表”适用于“无序数组中快速查找”。它们解决的是同一类问题（找数对），但使用的前提条件不同。

这个阶段最大的认知突破是：不要用一种解法去套所有题目，而是要根据题目特征选择合适的数据结构和算法模式。这也意味着我需要建立一套“分类思维”——看到一道题，先判断它属于哪一类，然后再调取对应的工具包。

## 第二章：数据结构——从“工具清单”到“武器库”

在刷题的前两周，我花了大量时间来理解 Java 中的各种数据结构。这个过程中最让我感到困惑的，是那些看起来相似但又不太一样的东西。

### 2.1 ArrayList 和 LinkedList 的选择题

第一次在 BFS 层序遍历中看到 `Queue<TreeNode> queue = new LinkedList<>();` 时，我不理解为什么这里不用 ArrayList。后来才知道，ArrayList 没有实现 Queue 接口，而且 `ArrayList.remove(0)` 的时间复杂度是 `O(n)`，而 `LinkedList.poll()` 是 `O(1)`。

这个经历让我明白：数据结构的选择不是随意的，它取决于两个因素——操作的频率和操作的复杂度。如果你需要频繁地按下标访问元素，用 ArrayList；如果你需要频繁地从头部移除元素，用 LinkedList（或更优的 ArrayDeque）。这不是机械记忆，而是在理解了每个数据结构的“底层物理结构”之后自然得出的结论。

### 2.2 int[] 和 Integer，length 和 size()

“基本类型 vs 引用类型”这个区分在刷题过程中反复出现。`int[]` 是连续的内存块，`ArrayList<Integer>` 是对象的容器。前者更快更省内存，后者更灵活但涉及装箱拆箱开销。

我逐渐形成了这样的认知：刷题时，优先考虑用数组（`int[]`），因为数据结构简单、访问快、内存小；只有在需要动态扩容、泛型支持或特殊 API 时，才使用集合类。

关于 `length` 和 `size()` 的区别，我犯过无数次错误后才形成肌肉记忆：数组用 `.length`（属性），String 和集合用 `.size()` 或 `.length()`（方法）。这看似是语法细节，背后反映的是“基本类型”和“对象类型”的本质差异——基本类型的数据直接存在栈里，对象的方法需要通过引用来调用。

## 第三章：递归思维——从“栈溢出”到“栈帧可视化”

递归是我学习过程中遇到的最大障碍之一。刚开始看归并排序的代码时，我完全无法理解程序为什么能一层层地“递”进去，又一层层地“归”回来。

### 3.1 归并排序：从“看不懂”到“画出递归树”

归并排序是我第一道认真学习的递归题。`mergeSort(left, mid)` 和 `mergeSort(mid+1, right)` 这两行代码，就像两个黑洞——程序钻进去之后，又莫名其妙地回来了。

转折点在于我画了一棵“递归调用树”。当我把 `[5, 2, 3, 1]` 的整个递归过程画在纸上时，我突然理解了什么叫“栈帧”。每一层递归调用都有自己独立的 `left`、`right`、`mid` 变量，它们各自存在各自的栈帧里，互不干扰。

我学到的第二课：递归的本质是“把大问题拆成结构相同的小问题”。只要搞清楚了“终止条件”和“递推公式”，剩下的由计算机自动完成。理解递归的关键不是跟踪每一次调用的具体数值，而是确信：子问题能解决，父问题就能解决。

### 3.2 从归并排序到最近公共祖先

最近公共祖先（LCA）这道题，让我看到了递归在树结构中的威力。代码只有几行：分别递归处理左子树和右子树，然后根据左右返回的结果，决定当前节点是不是答案。

第一次写这题时，我不明白为什么 `left != null && right != null` 时返回 `root`。后来我明白了，这实际上是在说：“如果左右子树各找到了一个目标节点，说明当前节点就是它们的汇聚点。”这种“信使汇报机制”的思维模型，是我至今仍在使用的重要工具。

这个阶段我的认知升级是：递归函数的返回值不是“结果”，而是“消息”。底层节点向上传递消息，高层节点根据收到的消息做出决策。理解了这一点，很多树形 DP 和回溯问题都变得清晰了。

## 第四章：回溯法——从“理解模板”到“灵活变形”

全排列是我第一次系统接触回溯法。我当时最困惑的是：为什么递归调用完之后要撤销选择？为什么路径要不断地 add 和 remove？

### 4.1 全排列中的“手电筒”比喻

我在网上看到过一个比喻：想象你在一个黑暗的迷宫里，左手拿着一个手电筒（路径），右手拿着一根粉笔（标记）。手电筒照亮的路径就是当前的选择，粉笔标记的就是 used 数组。当你走到死路时，你需要退回来，关掉手电筒（remove），擦掉粉笔标记（used[i]=false），然后尝试另一条路。

这个比喻让我真正理解了“回溯”二字的含义——不是简单的递归，而是“尝试-记录-递归-撤回-再尝试”的完整周期。没有 remove，路径会不停地膨胀，永远回不到正确状态。

### 4.2 从全排列到子集：startIndex 的诞生

做完全排列之后，我很快遇到了子集问题。一开始我试图用 used 数组去解，但发现出现了大量的重复结果（`[1,2]` 和 `[2,1]` 都被生成了）。

关键的顿悟是：子集不关心顺序，只关心组合。如果我们在每一层递归中，强制规定“只能选择下标大于等于当前位置的元素”，那么 `[2,1]` 就永远不会出现，因为当 `startIndex` 变成 1 后，就再也看不到下标 0 的 1 了。

`startIndex` 这个参数看起来很小，但它体现了一种重要的思维转变：有时候，不是算法本身不够强大，而是没有通过参数来约束搜索空间。给递归函数加上一个“起点”参数，就可以控制探索的范围和方向。

### 4.3 组合总和的“剪枝”艺术

组合总和允许重复取同一个数字，但这导致了一个新的问题：如果不做任何约束，程序会产生无限制的递归。解决方法是两个：一是限制递归深度（target 不断减少，直到为 0），二是提前终止不可能的分支（当 `target - nums[i] < 0` 时直接跳过）。

这个阶段我学到的是：回溯算法不仅仅是枚举所有可能性，更是“有策略地裁剪掉不可能的分支”。剪枝的好坏直接决定了程序的运行效率——不剪枝可能会超时，剪得太狠可能会漏解。

## 第五章：动态规划——从“填表”到“理解状态”

最长公共子序列（LCS）是我第一道正规的动态规划题。刚开始我对 `dp[i][j]` 的定义感到困惑：i 和 j 是什么意思？为什么要从 1 开始循环？为什么空字符串要占一行一列？

### 5.1 二维 DP 表格的“物理意义”

我花了很多时间去理解 LCS 的 DP 表格。表格的行代表 text1 的前缀，列代表 text2 的前缀。`dp[i][j]` 存储的是“这两个前缀的最长公共子序列长度”。

关键的推理链条是：

- 如果 `text1[i-1] == text2[j-1]`，这两个字符可以配对，所以答案就是“去掉这两个字符后的最优解 + 1”。
- 如果不相等，这两个字符不可能同时出现在公共子序列中，所以至少有一个是废物，取“扔掉 text1 的当前字符”和“扔掉 text2 的当前字符”两种方案中较大的一个。

这两个规则推导出来后，整个 DP 方程就自然浮现了。我不再需要死记 `dp[i][j] = max(dp[i-1][j], dp[i][j-1])`，而是能够自己在心里推导出来。

这个阶段最大的认知是：DP 不是魔术，它本质上是“把暴力搜索的结果存起来复用”。如果你能写出暴力递归，那么 DP 就是把这个递归的中间状态记录下来，避免重复计算。

### 5.2 从二维 DP 到一维 DP

当面试官问“空间复杂度能否优化到 O(n)”时，我最初是茫然的。但当我仔细观察填表顺序，发现 `dp[i][j]` 只依赖于上一行和当前行的左边时，我理解了“滚动数组”的原理。

这个优化过程让我意识到：理解算法不等于优化算法。但优化的前提是深刻理解数据的流向和依赖关系。如果连二维表格的填表顺序都没搞清楚，是不可能做出一维优化的。

## 第六章：广度优先搜索——从“二叉树”到“矩阵”到“抽象图”

BFS 我学了三遍。第一遍是二叉树的层序遍历，第二遍是腐烂的橘子（矩阵多源 BFS），第三遍是课程表（抽象图拓扑排序）。

### 6.1 二叉树 BFS：最标准的“分层遍历”

二叉树层序遍历让我学会了 Queue 和 levelSize 的快照机制。关键是：在处理当前层时，必须提前记录 `queue.size()`，因为内层循环会不断地向队列中添加下一层的节点。

核心思想是：队列不仅用来存储节点，还用来表示“层级边界”。`levelSize` 就相当于一个“层分隔符”，保证了每轮循环只处理同一层的节点。

### 6.2 矩阵 BFS：多源扩散

腐烂橘子中的 BFS 是多源的。最初我把所有腐烂橘子都加入队列，然后统一进行 BFS 扩散。这相当于在二叉树的层序遍历中，同时从多个根节点出发。

关键技巧是：用 `grid[i][j] = 2` 来代替 visited 数组。这种原地修改的方式，既节省空间，又简洁明了。

### 6.3 拓扑排序 BFS：入度驱动的扩散

课程表是抽象图上的 BFS。这里没有上下左右四个方向，取而代之的是“依赖关系链”。节点没有入队资格，只有当它的入度降为零时才能入队。

这个阶段的认知跃迁是：BFS 的精髓不是“物理上的扩散”，而是“状态上的传递”。二叉树中，父节点传递给子节点的是“层级信息”；矩阵中，腐烂橘子传递给新鲜橘子的是“腐烂状态”；课程表中，已学课程传递给后续课程的是“入度减一”。这三者虽然在表现形式上差异巨大，但本质都是 BFS 的“状态传递”模型。

## 第七章：贪心算法——从“区间划分”到“最远边界”

划分字母区间让我第一次接触贪心。贪心的核心是“局部最优解构成全局最优解”——不需要回溯，不需要 DP，只需要在每个步骤做出看似最有利的选择。

### 7.1 “最远边界”的逻辑

先扫描一遍字符串，记录每个字母的最后一处位置。然后再次扫描，维护当前区间的“最远截止位置”。当 `i == 最远截止位置` 时，下刀。

理解这题的关键是：当前片段内的所有字母，其最后出现位置的最大值，就是这个片段必须截止的最晚时刻。一旦扫描到这个时刻，就可以放心下刀，因为任何延迟都会导致某个字母出现在后面的片段中。

### 7.2 贪心的“勇气”——为什么敢这样切？

贪心最考验的不是算法能力，而是“证明能力”。我当时问自己：凭什么在 `i == end` 时下刀就一定是最优解？

原因在于：越早切，片段越多；切得越晚，片段越少。既然题目要求“尽可能多”，那么只要条件满足，就应该立刻切。这个结论不需要复杂的数学证明，只需要逻辑推演。

这个阶段我学到的是：贪心的难点不在于写代码，而在于“能不能证明当前的选择不会影响未来的最优解”。如果能证明，那就放心写。

## 第八章：二分查找——从“标准版”到“旋转数组”

二分查找是我最近刚攻克的模块。从标准二分（LeetCode 704）到旋转数组找目标（LeetCode 33），再到旋转数组找最小值（LeetCode 153），这一套下来让我对边界条件有了更深刻的理解。

### 8.1 循环条件的抉择：<= 还是 <

在标准二分中，我使用 `while (left <= right)`，因为这是左闭右闭区间，当 `left == right` 时还需要检查那个剩余的元素。

而在找最小值的旋转数组中，我使用 `while (left < right)`，因为当 `left == right` 时，那个位置已经是最小值了，不需要再进循环。

这个差异让我明白：循环条件不是随意的，它取决于“区间定义”和“终止条件”。左闭右闭、左闭右开、`<=`、`<`，这些选择背后都对应着精确的数学逻辑。

### 8.2 旋转数组的“分段有序”判断

旋转数组最核心的观察是：数组虽然整体无序，但“至少有一半是升序的”。利用这个性质，我们可以在每次循环中确定安全区间，然后决定目标在不在其中。

刚开始我完全无法理解这个逻辑，直到我自己画了几种旋转情况的数组，手动执行了几次二分，我才开始相信这个结论。反复推演让我明白了一个道理：二分查找的本质不是“判断 target 在哪”，而是“排除掉不可能的那一半”。只要能找到某个不变量（比如“左半边升序”），就能安全地排除另一半。

## 第九章：图论——从“入度”到“环检测”

课程表是图论入门，拓扑排序是处理依赖关系的标准工具。

### 9.1 Kahn 算法的“物理意义”

Kahn 算法的本质是“从没有依赖的节点开始，逐一移除，并更新依赖关系”。

我把它类比成“剥洋葱”——先找到最外层（入度为 0 的节点），剥掉它，然后发现新的外层，继续剥。如果到最后还有剥不掉的（入度大于 0），说明里面是个死结（有环）。

### 9.2 入度和邻接表的协同

入度数组用于判断“能否学习”，邻接表用于查询“学完后影响谁”。两者配合，构成了完整的依赖关系处理闭环。

这个过程中最让我感叹的是：无论你学了多少种数据结构，真正解决问题的往往不是单一的数据结构，而是它们的组合。入度数组提供判断依据，邻接表提供查询能力，队列提供处理顺序，三者缺一不可。

## 第十章：对未来的思考

学到现在，我已经初步建立了一个算法知识体系的大框架：

- 数组/字符串：双指针（相向、同向）、哈希表、前缀和、滑动窗口
- 链表：反转、合并、快慢指针
- 树：DFS、BFS、递归遍历、层次遍历、最近公共祖先、二叉搜索树
- 回溯法：全排列、子集、组合、剪枝
- 动态规划：一维/二维 DP、状态转移、滚动数组
- 贪心：区间划分、最远边界
- 二分查找：标准二分、旋转数组二分
- 图论：拓扑排序、环检测

接下来我需要攻克的还有：更复杂的 DP（如背包问题、编辑距离）、图论的其他应用（最短路径、并查集）、滑动窗口的进阶题型等。但有了现在这个知识基础，我相信面对任何新题，至少能有“从哪个方向切入”的判断力。

## 结语：算法的价值，不在代码本身

回顾这一个月，我最大的收获其实不是会做多少道题，而是建立了一种“算法式的思维方式”。

以前遇到复杂问题，我的第一反应是“找现成的工具或模板”。现在，我会下意识地拆解问题的结构：哪些是变量？哪些是约束？数据的流向是什么样的？我有没有见过类似的问题？

算法训练培养的不是记忆力，而是抽象能力和逻辑推理能力。每解决一道题，都是在强化这种“从混沌中理清结构”的能力。

我学到的最后一课：算法不是目的，它是训练思维的工具。能快速写出代码固然重要，但真正有价值的是当你面对一个陌生问题时，能够冷静地拆解它、分类它、找到合适的工具，并且有信心一步步推进，直到解决问题。

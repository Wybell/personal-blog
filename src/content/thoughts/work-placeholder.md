实习刚开始的那几天，我每天早上在地铁上都在想一个问题：“如果今天又卡住了怎么办？”

这个念头在我脑子里转了一个多月。事实上，刚开始那段时间确实每天都在卡住。拉代码卡在 SSH 配置上，折腾了半天才改用 HTTP；跑后端卡在 Nacos 上，搞不清命名空间和配置中心有什么区别；跑前端卡在代理上，写了一行 target 地址写错了 IP。那些在学校里觉得“这有什么难的”的事情，一到真实环境里就全变成了让人头疼的问题。

最夸张的一次，我在测试环境改一个前端展示 bug，改了代码、发了 MR、部署了测试环境，结果页面还是不对。我和测试同事在群里来回确认了好几轮，最后发现是浏览器缓存没清，代码本身已经好了。这种小事在整个实习过程中反复出现，它们不难，但足够消磨耐心。每一次我都在心里对自己说：“下次要记得先清缓存。”然后下一次照样忘记。

导师不会直接告诉我答案。这是他一开始就跟我说清楚的做法：“你自己先查，查不到再来找我。”这句话听起来很简单，做起来却很难。因为“先查”意味着你可能要花半个小时、一个小时去翻日志、看源码、搜文档，最后发现只是一个小疏忽。你可能会觉得自己浪费时间，但几次之后你会发现，那些“浪费”掉的时间其实是在帮你建立对代码库的熟悉感。我现在能说出某个功能对应的 Mapper 和 Controller 在哪个包里，大部分原因就是那段时间“浪费”出来的。

有一个 bug 我印象很深，到现在都还记得。那是一个审批流的待办生成问题：部门领导审批通过后，下一个节点的待办应该自动产生，但在测试环境中经常不出现。我一开始怀疑是代码逻辑错了，对照着业务规则把状态流转理了一遍，发现没问题。后来又怀疑是数据库事务没提交，改了事务传播行为，还是不行。我在本地跑了多次，偶尔能复现，偶尔不能。最让人困惑的是，打断点调试的时候它总是好的，一正常运行就又出问题。这种“打断点就好、不打断点就坏”的现象让我意识到问题出在异步时序上——两个异步任务，第一个还没写完数据库，第二个就开始读了。我调整了任务的执行顺序，让第一个任务完成后显式触发第二个，问题才解决。这不是什么大问题，但解决它让我理解了“定位问题”和“写代码”真的是两回事。写代码是从零到一，定位问题是在一团乱麻里找到那根线头。

还有一个让我印象深刻的场景，是和移动端同事联调。当时做了一个消息一键已阅的功能，接口逻辑很简单：批量更新当前用户所有未读消息的状态。后端测试没问题，我在 Swagger 上试了好几次都返回成功，但移动端同事说调不通。我把接口路径、请求方式、参数名对了一遍又一遍，都没问题。折腾了一个下午，最后发现是前端的 baseUrl 配置错了，指向了测试环境网关，而我部署的代码在开发环境注册中心，两个环境不一致，导致请求打到了另一个实例。这件事让我意识到，在真实项目中，“联调”这件看起来简单的事情，往往比写代码本身更花时间。因为你不仅需要确保自己是对的，还需要确保别人知道你哪里是对的。

前几周我几乎什么都靠 AI。代码写不出来靠 AI，bug 查不出来靠 AI，SQL 写复杂了靠 AI。我甚至能感觉到自己在慢慢依赖它——只要它给出了答案，我就直接用了，连思考的过程都省了。但后来有一次，AI 给了我一版看起来很正确的代码，我在测试环境跑了一遍，通过了，就提交了 MR。Code Review 的时候，同事指出来说“你这个 SQL 在数据量为零的时候会报空指针”，我仔细一看，AI 写的代码确实没有处理空集合的情况。这件事之后我开始重新思考自己跟 AI 的关系：它不是错在逻辑上，而是错在没有考虑到真实环境的边界条件，而我作为提交代码的人，本应该发现这个问题。从那以后我给自己定了一个规矩：AI 给的代码，必须手打一遍才能用。很慢，但每一次都能发现一两处它没想周全的地方。

实习的另一个收获，是亲眼看到了“代码是怎么变成线上服务的”。以前在学校做项目，写完代码、push 到 GitHub 就结束了，后面的事情从来没想过。但在公司，提交代码只是整个流程的第一步。你需要发起 MR，等同事 review，修改意见，再重新提交，合并到主分支，Jenkins 自动构建，部署到测试环境，测试人员验证，最后才能发版上线。每一步都有明确的责任人和校验标准。我记得第一次走完整个流程的时候，看着自己写的接口在线上环境真正被调用起来，那种踏实感和成就感，和作业拿了高分是完全不一样的。

当然也有很累的时候。通勤单程一个半小时，每天早上六点半起床，在地铁上摇摇晃晃地刷面经或看技术文章。有时候加班到晚上八九点，出了公司门天已经黑了，整个人在回程的地铁上都是放空的。有一天我在地铁上看到窗外熟悉的站台，突然觉得这条路好像已经走了很久——其实才一个月出头。但很奇怪，回头看的时候，那些疲惫好像也不算白费。

这段实习让我对公司开发流程有了更完整的认知。从 TAPD 接需求，到 GitLab 提 MR，到 Jenkins 自动构建，到 Nacos 服务注册，再到 Swagger 接口联调——每一个环节我都有了真实操作过的经验。这种“全链路”的体验，是学校项目给不了的。以前我对微服务架构的认知停留在书本上，知道什么是服务注册、什么是配置中心，但只有在真实项目中碰到过 Nacos 注册失败、Feign 调用超时、配置没刷新生效这些问题之后，我才真正理解了这些组件的边界条件和设计权衡。

还有一个感受是，和不同角色的人协作比写代码更考验耐心。产品经理可能说不清需求细节，测试人员可能比你更熟悉系统的边界行为，前端同事可能用了一套和你预期不一样的参数格式。你需要听懂别人在说什么，也需要让别人听懂你在说什么。这种能力比学会一个新的注解更花时间磨练，但也更接近“工作”本身。

项目交付前的那段时间，发版比平时频繁得多。有时候周一改的 bug 周三就发上线了，有时候周五刚发完一版，下周一又需要出一版紧急修复。我开始理解“周迭代”为什么会在交付期变成“随时发版”——不是因为团队混乱，而是因为客户在真实使用，反馈来得比测试环境快得多。这种“你的代码在被人用”的感觉，和作业被老师批改完全是两回事。

马上就要秋招了，说没有压力是不可能的。算法刷得不够多，八股背得也不够熟，身边的同学有的准备得更充分。但实习这段经历至少让我明白了一件事：我能做的事情，比我知道的东西要多。那些代码不是我背出来的，是我一行一行写出来的；那些 bug 不是我背出来的，是我一个一个查出来的；那些接口不是我背出来的，是我一个一个调通的。这些东西不会出现在八股文里，但它们组成了我敢去面试的底气。

如果问我实习最大的收获是什么，大概不是某个具体的技术点，而是一种确信——确信自己能在真实的环境里解决问题，确信自己能在这个行业里站住脚。虽然现在还远算不上熟练，方向是对的。只要方向是对的，慢一点也没关系。
